# 画面設計書 — 使い方

## 使い方

本ページは本フォルダー（`screen-design/`）配下の各テンプレートページの**書き方の指南**。
04〜06系ドキュメントと同じ「[Template]／[Sample]／[使い方]」の3分類とし、[使い方]は
[Template]／[Sample]と同じ階層（本フォルダー直下）に置く。08系は1機能あたり複数ページ
（表紙・画面設計・チェック処理概要・帳票設計書・プレビュー画面設計書・更新条件表・
検索条件表）に分かれるため、それら全ページ分の記入例を本ページ1枚にまとめている。

### フォルダー＝機能単位、ファイル＝画面単位（ファイル名は画面ID始まり）

KCCSサンプル（`Ⅶ.ｼｽﾃﾑ機能設計書`）と同じ構成にする。**1機能＝1フォルダー**とし、その機能に
属する複数画面の設計書を同じフォルダーにまとめる。**フォルダー名は機能ID**（`{function-id}_{function-name}/`）、
**その配下の各設計書ファイル名は画面ID始まり**（`{screen-id}_01_screen-design.md` 等）とする。
表紙（`index.md`）だけはフォルダーに1枚で、機能に属する全画面で共有する。

| 対象 | 命名 | 単位 | KCCSサンプルでの対応 |
| ---- | ---- | ---- | -------------------- |
| フォルダー | `{function-id}_{function-name}/` | 1機能 | `AZS110_注文照会/` |
| 表紙（共通） | `index.md` | 1機能に1枚 | `AZS110_00_表紙.xlsx` |
| 機能概要 | `index.md`「1. 機能概要」 | 1機能に1枚 | `AZS110_00C_注文照会_機能構成.xlsx` |
| 画面設計 | `{screen-id}_01_screen-design.md` | 1画面 | `AZS111_01C_画面設計_….xlsx` |
| チェック処理概要 | `{screen-id}_02_check-process-overview.md` | 1画面 | `AZS111_02C_ﾁｪｯｸ処理概要_….xlsx` |
| 帳票設計書 | `{screen-id}_03_report-design_01.md` | 1画面×1帳票 | `AZS111_03C_ﾌｧｲﾙ出力_….xlsx` |
| プレビュー画面設計書 | `{screen-id}_04_preview-screen-design_01.md` | 1画面×1印刷用画面 | （原本に該当なし。本サイト独自。`{screen-id}`は帳票設計書と同じく押下元画面の画面ID、末尾の連番は重複回避の採番） |
| 更新条件表 | `{screen-id}_05_update-condition-table.md` | 1画面 | `AZS111_05D_更新条件表_….xlsx` |
| 検索条件表 | `{screen-id}_06_search-condition-table.md` | 1画面 | `AZS111_06D_検索条件表_….xlsx` |

**画面を追加する手順**：`{screen-id}_01_…`〜`{screen-id}_06_…`のうち必要なページを、
その画面の画面IDを先頭にしたファイル名で複製し、`index.md`の「2. 関連画面一覧」と
「4. 設計書構成」に行を追加する（`No.`は表全体を通した連番なので1から振り直す）。
**フォルダーは増やさない**（同じ機能の画面は同じフォルダーに置く）。

**全画面が全ページを持つ必要はない**。その画面に無い設計書はファイル自体を作らず、
`index.md`「4. 設計書構成」の該当行を「対象外」とし、理由を書く（KCCSサンプルでも
`AZS141`のように`01C_画面設計`を持たず`02C`／`05D`／`06D`だけの画面が存在する）。
実データの記入例は[\[Sample\]P021A_受注残一覧表](<[Sample]P021A_受注残一覧表/index.md>)
（`JZ01`＝プレビュー画面設計書のみ対象外／`JZ01P`＝プレビュー画面設計書のみ作成）および
[\[Sample\]S032A_積送日数マスタ](<[Sample]S032A_積送日数マスタ/index.md>)（`M32`＝プレビュー画面設計書のみ対象外）を参照。

| フォルダー／ファイル | 位置づけ | 中身 |
| ------------------- | -------- | ---- |
| [\[Template\]{function-id}\_{function-name}](<[Template]{機能ID}_{機能名}/index.md>) | 記入用の空テンプレート | 実データを持たない、ほぼ空のひな形（表紙＋画面単位の6種のページ） |
| [\[Sample\]S021G_売上予定管理](<[Sample]S021G_売上予定管理/index.md>) | 実データ例（1画面） | SC納期管理の実機能（`S021G`／画面`U31`・`U31DL`）を記入した記入例。画面設計ページを持つ画面が1つだけのケース |
| [\[Sample\]S032A_積送日数マスタ](<[Sample]S032A_積送日数マスタ/index.md>) | 実データ例（更新系） | SC納期管理の実機能（`S032A`／画面`M32`・帳票`M32DL`）を記入した記入例。**追加・更新・削除・一括取込（アップロード）を持つマスターメンテナンス系**のケース。更新条件表は単一ファイル形式 |
| [\[Sample\]P021A_受注残一覧表](<[Sample]P021A_受注残一覧表/index.md>) | 実データ例（複数画面） | SC納期管理の実機能（`P021A`／画面`JZ01`・`JZ01P`・帳票`JZ01DLL`）を記入した記入例。**1機能に複数画面が属し、印刷用画面（プレビュー画面設計書）と帳票を両方持つ**ケース |
| **本ページ（\[使い方\]）** | 書き方の指南 | 各ページ・各項目の意味とプレースホルダによる記入例 |
| [使い方]（ベトナム語版） | 上記の翻訳版 | 同内容のベトナム語訳（ベトナム側メンバー向け。成果物本体は日本語で記入する） |

## 共通の記入ルール

「ほか」「等」での省略禁止／1件＝1行／グループ化した行でもキー列を空欄にしない、の3点は [記述ルール 節10「列挙と行の書き方」](<../../05-システム設計書（全体）/5-9_標準設計書/5-9-1_記述ルール/[Sample]5-9-1_記述ルール.md#10-列挙と行の書き方一覧表の共通ルール>) を正とする（各ページに重複記載しない）。

## 1. 設計書構成（index.md）

ファイル名は`{function-id}_00_cover.md`ではなく`index.md`とする（`cover`→`index`へ
改称。目次用途のページであることを示す。バッチ処理定義書・DB(SQL)処理定義書と共通のルール）。従来
ページ末尾にあった「文書情報＋改定履歴」表（ファイル自体の改訂履歴）は削除する。

本ページは機能に属する全画面で共有する**唯一の機能単位ページ**であり、画面単位ページに
書くと画面数だけ同じ内容が重複してしまう情報（機能概要・関連画面一覧・関連帳票一覧・
設計書構成）を、すべて本ページに集約する。

「1. 機能概要」は、旧版では[画面設計](<[Template]{機能ID}_{機能名}/{画面ID}_01_画面設計.md>)側の「機能概要」欄に
置いていたが、画面単位ファイルへの分割に伴い本ページへ移した（画面が2つ以上ある機能で
同じ機能概要が各画面ファイルに重複するため）。KCCS原本でも機能概要は画面設計シートではなく
機能単位の「機能構成（00C）」側にあり、原本の構成と一致する。記入例：

| 項目            | 内容                                                                             |
| --------------- | -------------------------------------------------------------------------------- |
| 機能ID          | F001                                                                             |
| 機能名          | F001：〇〇照会                                                                   |
| 概要            | 〇〇情報の登録を行う。〇〇情報を一覧表示し、選択された各〇〇情報の詳細画面を表示する。一覧画面ではデータの一括更新を可能とし、詳細画面では明細単位での更新を可能とする。 |
| 作成者 / 作成日 | 山田太郎 / 2020-01-01                                                            |
| 更新者 / 更新日 | 山田太郎 / 2020-02-01                                                            |

*記入方法：*`機能ID`**は自己採番しない**。客先提供の機能一覧（`納期管理‗機能一覧.xlsx`の`機能分類`シート）から
取得し、[システム機能一覧]（6.1）と一致させる。（`機能分類`列は本ページ・6.1双方から削除済み。下記8.1の注記参照）

「2. 関連画面一覧」「3. 関連帳票一覧」（本サイト独自の追加。KCCS原本の表紙にはない）は、旧版では
[画面設計](<[Template]{機能ID}_{機能名}/{画面ID}_01_画面設計.md>)側に置いていたが、本ドラフトでは`index.md`
側へ移した。関連画面一覧は1つの機能ID配下に複数の画面IDが対応するのが基本構成であり、本表でその
対応関係を管理する（ボタン押下で**別機能**の画面へ遷移する場合、その遷移先は本表には含めない）。
本フォルダーのファイル名は画面ID始まりであるため、本表の「設計書page」列は
その画面の`{screen-id}_01_screen-design.md`へのリンクとなる（画面設計ページを作らない画面は、
その画面の仕様を記載しているページ＝帳票設計書等へリンクし、理由を備考に書く）。
関連帳票一覧は1帳票＝1行。**節番号を全機能で固定するため、対象が無い機能でも節そのものは必ず設け、
本文に「なし（＋理由）」と記載する**（節ごと省くと機能によって以降の節番号がずれ、機能間で
`index.md`の構成が比較できなくなるため）。画面ID・帳票の
一覧の正は[画面・帳票一覧（6.2）](<../../06-システム設計書（一覧、管理台帳）/6-2_画面・帳票一覧/[Sample]6-2_画面・帳票一覧.md>)であり、
`index.md`側は本機能に属する範囲の抜粋（設計書ページへのリンク集）という位置づけ。

「4. 設計書構成」（旧「1. 設計書構成」）は、本機能で作成する**画面単位の設計書（Markdownファイル）を
画面ID順に列挙する表**（記入例は[Template]/[Sample]の`index.md`そのものを参照）。
節番号は全機能で固定（1. 機能概要／2. 関連画面一覧／3. 関連帳票一覧／4. 設計書構成）。

- **`No.`列は表全体を通した1からの連番**とする（KCCS基本9種のNo.ではない。画面を追加・削除したら
  1から振り直す）。
- **`画面ID`列を持ち1画面×1設計書＝1行**で列挙する（共通ルール「複数件をまとめて記載しない」に従い、
  1つのセルに複数画面分のリンクを並べない。またグループ化した行でもキー列を空欄にしないルールに従い、
  `画面ID`は同じ画面の行すべてに繰り返し記入する）。
- 並び順は**画面ID順**、同一画面内はファイル番号順（01 画面設計→02 チェック処理概要→
  03 帳票設計書→04 プレビュー画面設計書→05 更新条件表→06 検索条件表）。
- **本ページ（`index.md`）自体は本表に含めない。** 表紙・機能概要は機能単位のページであり、
  本表は「画面ごとに作成するMarkdownファイルの一覧」だからである（旧版ではKCCS基本9種の
  チェックリストとして「機能定義書(機能概要)」の行を置き`index.md`自身へリンクしていたが、
  自己参照になり一覧の目的とも合わないため行ごと削除した。機能概要の所在は「1. 機能概要」で自明）。
- 作成したページには「作成」＋ファイルへのリンクを、作成しなかったページには「対象外」＋
  `本フォルダでの対応ページ`欄に`（理由）`を記入する（ファイル自体は作らない）。
- **列は上記5列のみとし、`備考`等の列を独自に追加しない**（設計書をDBへ取り込む際の項目定義と
  ずれるため。記載したい補足は`（理由）`として対応ページ欄に収める）。

「5. 改訂履歴（設計内容）」は、この機能自体の**設計内容の改訂**を積み上げる欄（テンプレート編集の
改定履歴＝旧・下部の「改定履歴」表とは別物。`index`化に伴い下部の「改定履歴」表自体は削除したが、
このⅡ節は維持する）。列は記述ルール 節1 No.10 と同じ 6 列（Version｜計画書No.｜改訂日｜改訂内容｜担当者｜課題No./備考）。記入例：

| Version | 計画書No. | 改訂日 | 改訂内容 | 担当者 | 課題No./備考 |
| ------- | --------- | ------ | -------- | ------ | ------------ |
| 1.0 | K0000-XX001 | 2026-01-10 | 第1フェーズ対応による新規作成（画面A, 画面B, 画面C, 画面D, 画面E, 画面F） | 山田太郎 | |
| 1.1 | K0000-XX001 | 2026-02-01 | 第1フェーズ課題対応による修正 | 山田太郎 | No.xxx, No.xxx |

## 2. 画面設計（{screen-id}_01_screen-design.md）

**1画面＝1ファイル。** ファイル名の先頭は本ページのヘッダーに記入する`画面ID`と一致させ、
機能に属する画面ごとに本ページを複製する（例：画面`U31`→`U31_01_screen-design.md`）。
ヘッダーの記入例：

| 項目            | 内容                        |
| --------------- | --------------------------- |
| 画面ID          | G001（ファイル名の先頭と一致させる） |
| 画面名          | 〇〇照会（一覧）            |
| 作成者 / 作成日 | 山田太郎 / 2020-01-01       |

「機能概要」「関連画面一覧」は`index.md`「1. 機能概要」「2. 関連画面一覧」へ移設した
（記入例は上記「1. 設計書構成」および[Sample]の`index.md`同節を参照）。本ページ側には表を置かず、
`index.md`への参照1行のみとする（機能単位の情報を画面数だけ重複させないため）。

### 4. 画面項目イベント詳細

ボタン押下・リンク押下等のイベントごとに、処理内容とメッセージを1行で記述する。

**「遷移先（機能ID／画面ID）」欄**：ボタン押下・リンク押下で**画面遷移が発生するイベントのみ**、遷移先を
機能ID／画面IDで記載し、遷移先の設計書とリンクできるようにする（同一機能内の画面なら画面IDのみ、
別機能なら`機能ID／画面ID`）。遷移が発生しないイベントは「－」とする。記入例：

| No. | 画面項目名 | イベント内容 | キー割当 | 遷移先（機能ID／画面ID） | 処理内容                                                                         | メッセージ                       |
| --- | ---------- | --------- | ------ | ------------------------ | ---------------------------------------------------------------------------------- | ---------------------------- |
| 1   | 検索       | ボタン押下  | －     | －（自画面を再表示）      | 検索項目に入力した条件で取得したデータを、画面の一覧に表示する。                   | －                           |
| 2   | クリア        | ボタン押下  | －     | －（遷移なし）            | 検索項目および明細をすべてクリアする。                                              | クリアします。よろしいですか？  |
| 8   | 削除       | ボタン押下  | －     | －（自画面を再表示）      | 一覧明細でチェックしたデータを削除する。また、紐づく関連情報が存在する場合は関連情報も併せて削除する。削除後、前回検索時の条件で再検索を行う。 | 削除します。よろしいですか？ |
| 13  | No.        | リンク押下   | －     | XXX112／GXXX002           | 押下したデータの詳細画面を新規ウィンドウで開く。既に同画面が開いている場合はそのタブに上書きする。 | －                           |

### 6. 画面項目制御・出力仕様

ボタン押下等の操作ごとに各画面項目の制御状態を記載する。凡例：`○`＝使用可、`△`＝使用不可、
`×`＝表示しない、`－`＝制御しない。

## 3. チェック処理概要（{screen-id}_02_check-process-overview.md）

**1画面＝1ファイル。** ファイル名の先頭はヘッダーの`画面ID / プログラムID`と一致させる。

チェックは契機（どのボタン押下時か）ごとに**表そのものを分ける**。見出しは`#### 【（ボタン名）押下時】`
の形式とし、1契機＝1表とする（1つの表に複数の契機を混在させない）。ボタン押下以外の契機
（フォーカスアウト、画面初期表示、明細行の追加等）も同じ形式で表を分ける。どの契機にも紐づかない
共通チェックがある場合のみ、最後に`#### 【契機共通】`の表を置く。どのボタンを押した時にどの項目で
エラーになるかが表単位で分かるようにするため。記入例：

「区分」欄はチェックの**種別**（必須チェック／形式チェック／存在チェック／上限チェック／桁数チェック／
排他チェック 等）を記入する。「レベル」欄は主に「エラー」（処理を中断する）と「ワーニング」

## 7. 検索条件表（{screen-id}_06_search-condition-table.md）

**1画面＝1ファイル。** ファイル名の先頭はヘッダーの`画面ID`と一致させる。
1画面から複数の検索（初期表示／一覧検索／明細取得等）が発生する場合、「検索条件表 No.1」
「検索条件表 No.2」…と検索単位ごとに分けて記述する。結合や抽出条件が無い単純な検索は
「該当なし」と明記してよい（下記No.2参照）。

### 契機×検索 対応表

**検索条件表は契機（ボタン）単位ではなく検索単位で作成し、契機との対応は本表で管理する。**
1つの契機が複数の検索を起動し、逆に1つの検索が複数の契機から共用されるため、契機単位で表を分けると
同じ検索を重複して書くことになるためである（実例：`S021G`では検索ボタン1つで11検索を実行し、
検索条件呼出と検索条件保存が同一検索を共用し、初期表示のようにボタンではない契機も存在する）。

本表は「どのボタンを押すとどの検索が動くか」を1か所で示すためのもので、検索条件表の本体（No.n）の
前に置く。記入例：

| 契機（ボタン・イベント） | 起動する検索条件表No. | 備考 |
| ------------------------ | --------------------- | ---- |
| 初期表示                 | No.2, No.3            | コンボボックスの選択肢生成。ボタン押下ではない契機 |
| 検索ボタン押下            | No.1, No.4            |      |
| 検索条件呼出ボタン押下    | No.5                  | No.5は検索条件保存ボタンと共用 |
| 検索条件保存ボタン押下    | No.5                  | 同上 |
| ダウンロードボタン押下    | 該当なし              | 新規SQLを発行せず直前の検索結果を再利用する |

*記入のポイント：*

- 契機は**ソースコードのイベントハンドラ単位**で洗い出す（`control_eventHandller`の分岐と、
  `initialEvent`／`reloadEvent`等のボタン以外の契機）。推測で契機を作らない。
- 検索を行わない契機（画面遷移のみ・更新のみ等）も**「該当なし」＋理由**を書いて行を残す。
  行が無いと「調査漏れ」なのか「検索が無い」のか区別できないため。
- 詳細化していない検索がある場合は「（記入：未作成）」とし、どこまで作成済みかを本表で示す。

## 8. 記入上の補足（KCCS原本との対応・逆生成時の注記）

[Template]／[Sample]の各ページには説明文・注記を書かない（成果物には設計内容のみを載せる）。
以下は、その説明・注記をまとめたもの。

### 8.1 設計書構成（index.md）

- **機能フォルダーの単位**：顧客要望により「ソースコードのパッケージ（モジュール）単位」
  （＝1 Javaパッケージ＝1機能＝1フォルダー、フラット構成）とし、機能分類単位のグループフォルダーは作らない。
- **配下のファイル名は機能IDではなく画面ID始まり**：1機能に複数画面が属するのが基本構成であり、
  ファイル名を機能ID始まり（旧：`{function-id}_01_screen-design.md`）にすると、2画面目以降を
  同じフォルダーに置けず（ファイル名が衝突する）、機能単位フォルダーの意味が失われていた。
  KCCSサンプルも同じ構成で、機能フォルダー（例：`AZS110_注文照会/`）配下の各設計書シートは
  画面ID始まり（`AZS111_01C_画面設計_…`／`AZS112_01C_画面設計_…`）で採番され、表紙
  （`AZS110_00_表紙.xlsx`）と機能構成（`AZS110_00C_…_機能構成.xlsx`）だけが機能ID始まりである。
  本サイトも同じ分担とし、**機能ID始まり＝`index.md`（表紙＋機能概要）のみ、画面単位の
  6ページはすべて画面ID始まり**に統一した。トークン順序の共通ルール（可変部`{}`が先、固定部が後）は
  そのまま維持される（`{screen-id}_01_screen-design.md`）。
  機能分類は[システム機能一覧](<../../06-システム設計書（一覧、管理台帳）/6-1_システム機能一覧/[Template]6-1_システム機能一覧.md>)の列として管理していたが、
  フォルダー構成に使われないままID／コードも割り当てられていなかったため、客先確認のうえ同表から削除した
  （経緯は`ID_No_採番監査.md`参照）。
- **「1. 上位文書」は廃止**：KCCS原本（全17機能で確認）には必ず存在するが、標準設計書（京セラ基幹
  システム標準書）・共通設計書・ルール文書・フロー設計書のいずれもRikkei側から参照できず、原設計書
  未受領の機能では永久に「不明」のまま埋まらない。実質的な情報価値がないため本サイトではセクション
  自体を作らない。
- **`{function-id}_00_cover.md`→`index.md`へ改名**（`cover`→`index`）：KCCS/PM
  フィードバックにより、本ページは目次用途のページと位置づけ、ページ末尾の「文書情報＋改定履歴」表
  （ファイル自体の改訂履歴）を削除した。ファイル名は他の連番ファイル（`{screen-id}_01_...`等）とは
  異なり、**番号・プレフィックスを付けず`index.md`のみ**とする。理由：mkdocsはフォルダーの入口ページ
  （そのフォルダーを開いたときに表示されるページ）として、正確に`index.md`という名前のファイルのみを
  自動認識する仕組みのため（`.pages`のnav順序制御とは別の、mkdocs本体の挙動）。`{function-id}_00_index.md`
  のようにプレフィックスを残すと、そのフォルダーの入口ページとして機能しなくなる（本サイトが使用する
  `awesome-pages`プラグインだけではこの機能を持たず、別途`mkdocs-section-index`プラグインの追加導入が
  必要になるため、追加導入なしで確実に機能する`index.md`（プレフィックスなし）を採用する）。
  バッチ処理定義書・DB(SQL)処理定義書も同じ理由で`index.md`（プレフィックスなし）に統一する。
- **「2. 関連画面一覧」「3. 関連帳票一覧」を新設**：KCCS/PMフィードバックにより、旧・画面設計ページに
  あった関連画面一覧を`index.md`側へ移設し、同様の構成で関連帳票一覧も新設した
  （詳細は8.2参照）。
- **「4. 設計書構成」（旧「1. 設計書構成」）の 作成有無 列**：KCCS原本では「Customer／Developer」の2列
  （それぞれの読み手＝顧客／開発者に開示する設計書かどうか）だったが、本サイトでは1列
  「作成有無（作成／対象外）」に統合した。KCCS原本を機能ごとに突き合わせた結果、Customer／Developer
  の値は機能によってバラバラで固定の対応表は存在せず、しかも原設計書未受領の機能ではRikkei側に
  判定材料がない。一方「本フォルダーで実際にそのページを作成したか」はフォルダーの中身から自己完結で
  判定できるため、この列に置き換えた。
- **「4. 設計書構成」の一覧**：KCCS基本の9種のうち、本サイトで**画面単位のMarkdownファイルとして
  作成し得る6種**（画面設計書／チェック処理概要／帳票設計書／プレビュー画面設計書／更新条件表／
  検索条件表）のみ記載する。除外している3種の理由は次のとおり。
    - **機能定義書(機能概要)**：機能単位の情報であり、画面単位のファイルにはならない。本サイトでは
      `index.md`「1. 機能概要」がその中身そのものであるため、本表に行を置くと`index.md`自身への
      自己参照になる。行ごと作らない。
    - **プログラム設計書／スペーシングチャート**：全17機能の原本表紙で常に対象外
      （Customer／Developer両方とも－）であり、本サイトのスコープにも入らない
      （「対象外」の行を残して埋めるのではなく、行ごと作らない）。
  各行には`画面ID`列を持たせ、1画面×1設計書＝1行で対応ページへ直接リンクする（画面単位ファイルへの
  分割前は画面設計書・帳票設計書の2行を「関連画面一覧」「関連帳票一覧」への参照で代替していたが、
  ファイル名が画面ID始まりになり本表からも画面ごとに一意にリンクできるようになったため、
  参照ではなく実リンクに戻した）。本表と「2. 関連画面一覧」「3. 関連帳票一覧」は見る軸が異なる
  （本表は「画面ごとにどの設計書ファイルを作成したか」、2／3は「どの画面・帳票があるか」）ため、
  重複しているわけではない。
- **「5. 改訂履歴（設計内容）」**：機能の設計内容そのものの改訂を積み上げる欄。旧・ページ末尾の
  「改定履歴」（Markdownドキュメント自体の更新履歴。`index`化に伴い削除）とは別物なので混同しない
  こと（このⅡ節自体は維持する）。

### 8.2 画面設計

- **「機能概要」欄は`index.md`へ移設**：KCCS原本でも機能概要は画面設計シートではなく別ファイル
  「機能構成（00C）」側にあり（ただし原本は機能単位ではなく機能分類（グループ）単位で記載）、
  機能単位の情報である。旧版では画面設計ページ側に置いていたが、画面単位ファイルへの分割に伴い
  `index.md`「1. 機能概要」へ移した（画面が2つ以上ある機能で同じ内容が画面数だけ重複するため）。
  結果として本サイトの分担もKCCS原本（機能構成＝機能単位／画面設計＝画面単位）と一致する。
- **「関連画面一覧」は`index.md`へ移設**：KCCS原本の表紙にはないセクション（本サイト
  独自の追加）だが、KCCS/PMフィードバックにより画面設計ページから`index.md`
  「2. 関連画面一覧」へ移した。1つの機能ID配下に
  複数の画面IDが対応するのが基本構成であり、本表でその対応関係を管理する。ボタン押下で**別機能**の
  画面へ遷移する場合、その遷移先は本表には含めない。
- **1画面＝1ファイル**：本ページは画面単位であり、ファイル名の先頭を画面IDとする
  （`{screen-id}_01_screen-design.md`）。機能に属する画面ごとに複製する。
- **「3. 画面表示仕様」**：KCCS原本ではこの位置に検索条件・結合条件等のDB取得ロジックが直接
  記載されるが、本サイトでは重複を避け[検索条件表](<[Template]{機能ID}_{機能名}/{画面ID}_06_検索条件表.md>)に集約し、
  本欄はリンクのみとする。
- **記載順**：KCCS原本と同じく Ⅳ（画面項目イベント詳細）→ Ⅴ（画面項目定義）の順に記載する。

### 8.3 参照エンティティ一覧（02／03／05／06 共通）

KCCS原本は A〜J／X1〜X6 等のテーブル別名（エイリアス）体系を持ち、各表の「参照先」列に記号で参照する。
この体系を持たないシステムでは、記号欄に実テーブル名（および画面ID）をそのまま記載する。

### 8.4 帳票設計書

KCCS原本のヘッダーは「機能ID」「ファイルID」の2項目のみ。本サイトでは他ページと体裁を揃えるため
「システムID」「作成日／作成者」を追加し、さらにKCCS様指摘を受けて「画面ID」「帳票ID」「帳票名」
「出力区分」「出力契機」を追加している。

- **名称を「ファイル出力設計書」から「帳票設計書」へ変更**：KCCS原本の名称は「ファイル出力設計書」
  だが、定義としては「帳票出力」が正しいとの指摘により、ページ名・表紙の設計書構成・文書情報の
  ドキュメント名をすべて「帳票設計書」に統一した。帳票とファイルの区別（レイアウト情報の有無）は
  ヘッダーの「出力区分」欄で表す。
- **「出力管理情報」欄は廃止**：不要との指摘により削除した。
- **1帳票＝1ファイル**：1パッケージ・1画面で複数帳票を出力する場合があるため、`_01`、`_02`…の
  連番ファイルで帳票ごとに独立させる。

### 8.5 更新条件表

KCCS原本ではテーブル1つ＝1シートで、更新概要／更新条件／更新項目が単一の見出し
「1. 更新条件表（機能単位）」の配下にまとまる（各小項目にローマ数字は付かない）。
本サイトでは1テーブル＝1ファイルとする（KCCS原本の「1テーブル＝1シート」に対応）。

**更新テーブル数によって単一ファイル／フォルダー＋indexを使い分ける**（2026-09-02のドラフトで
追加した方針。DB(SQL)処理定義書の更新条件表は元々テーブル数に関わらず単一ファイル内で
No.を増やす形式のため、この使い分けは画面設計書固有）。テーブルが1つだけなら
`{screen-id}_05_update-condition-table.md`という単一ファイルで完結させ、フォルダー・indexは作らない
（DB(SQL)処理定義書と同じ考え方）。テーブルが2つ以上になった時点で初めて
`{screen-id}_05_update-condition-table/`フォルダー＋`index.md`（テーブル一覧＋テーブルをまたぐ
振り分けロジックの置き場所）＋1テーブル1ファイルの構成へ切り替える。単一ファイルの場合と違い、
`index.md`自体は末尾「文書情報＋改定履歴」表を持たない（画面設計書の表紙等と同じ「目次ページには
ファイル自体の改訂履歴を持たせない」ルールに合わせる）。

### 8.6 リバースエンジニアリング（原設計書が無い機能）で記入する場合

- ソースコードに現れない情報（作成者・作成日等）は「不明」「未特定」と明記し、
  憶測で埋めない。
- エラーコードの採番体系を持たないシステム（メッセージが全てリテラル文字列）では、
  「エラーコード」列は全行「－」とし、他機能との体裁統一のため列自体は残す。
- 実機画面キャプチャが未取得の場合、「1. 画面レイアウト」には構成の箇条書きを記載し、
  取得後に画像へ差し替える。

    - `CheckForm()`の必須チェックは、事業部名の未選択を先に弾くため、後続の「9項目すべて未入力」の
      判定の最内側が**到達不能コード**になっている。ソース上のコメントにも`// 暫定バグ対策`と記載がある。
    - 「ダウンロード」「印刷」ボタンには`CheckForm()`が呼ばれず、検索条件未入力のままでも実行できる
      （「注残検索」とのチェックの強度差）。
    - `Search_Rule()`／`auto_chk()`は**フォーム上に存在しない8項目**
      （`DEFAULT_NO`／`AUTO_FLG`／`TORIHIKISAKI_CD`／`KESSAISAKI_CD`／`KESSAISAKI_RYAKUSHIKI_MEI`／
      `CHUMON_BANGO`／`KANREN_CHUBAN`／`EIGYO_KANRI_CD`）を参照しており、呼び出されればJavaScriptエラーと
      なるデッドコードである。`LYR03_DEF_TBL`のSQLが同じ項目を保持していることから、他画面からの流用時に
      取り残されたものと推測される。
    - `executeSubmit()`は`return(true);`のみでチェックを行わない（入り口だけが用意された状態）。
    - 一覧グリッドの列見出しに「型代」が2列連続で現れ、ソース上も区別が付かない（帳票`JZ01DLL`側では
      「型代」「型代区分」と正しく区別されている）。
    - ダウンロードのファイル名`DJZ_yyyyMMdd.xls`は時刻を含まないため、同一日に複数回出力すると
      ファイル名が重複する。
    - サーバー側（`lyr07_JZ01Servlet`／`lyr07_JZ01Control`）に業務バリデーションがなく、実質的な
      チェックはすべてJSPのJavaScriptで行われている（S021G・S032Aと同じ申し送り事項）。
- **未記入として残した箇所**：`LIST_SEIDEN`の`ORDER BY`句、検索条件の演算子の全件突き合わせ、
  「残金額」の算出式、印刷仕様（用紙サイズ・向き・改ページ）、チェックボックス2項目の画面ラベルは
  ソースから確定できなかったため`（記入：<理由>）`形式で残している（共通ルールの3番目の書き方）。
- **6.2との差異（要確認事項）**：[画面・帳票一覧（6.2）](<../../06-システム設計書（一覧、管理台帳）/6-2_画面・帳票一覧/[Sample]6-2_画面・帳票一覧.md>)は
  `P021A`について画面`JZ01`の1行のみを登録しており、画面`JZ01P`と帳票`JZ01DLL`の行がない。
  ソース上は`lyr07_JZ01P.jsp`・`lyr07_JZ01DLL.jsp`が実在し`lyr07_JZ01Servlet`から遷移するため、
  6.2側への追加が必要と思われる。**なお同様の不足はP021Aに限らず、ソースを確認した39パッケージのうち
  29パッケージが複数のJSPを持つ**（6.2は各機能1画面しか登録していない）。6.2全体の見直しが必要な
  規模の課題であるため、別途対応すること。
