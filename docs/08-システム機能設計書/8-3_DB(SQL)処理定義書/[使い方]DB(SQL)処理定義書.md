# DB(SQL)処理定義書 — 使い方

## 使い方

本ページは本フォルダー（`db-sql-processing-spec/`）配下の各テンプレートページ（01〜05）の
**書き方の指南**。04〜06系ドキュメントと同じく、[使い方]は[Template]／[Sample]と同じ階層
（本フォルダー直下）に置く。1パッケージ（または単独プロシージャー／ファンクション）＝1フォルダーに
5ページ分かれるため、それら全ページ分の記入例を本ページ1枚にまとめている。

| フォルダー／ファイル | 位置づけ | 中身 |
| ------------------- | -------- | ---- |
| [\[Template\]{package-id}\_{package-name}](<[Template]{パッケージID}_{パッケージ名}/index.md>) | 記入用の空テンプレート | 実データを持たない、ほぼ空のひな形（5ページ） |
| [\[Sample\]NOUKI_PKG](<[Sample]NOUKI_PKG/index.md>) | 実データ例 | SC納期管理の実パッケージ（NOUKI_PKG）を記入した記入例 |
| **本ページ（\[使い方\]）** | 書き方の指南 | 各ページ・各項目の意味とプレースホルダによる記入例 |
| [使い方]（ベトナム語版） | 上記の翻訳版 | 同内容のベトナム語訳（ベトナム側メンバー向け。成果物本体は日本語で記入する） |

以下は**架空のパッケージ「PKG_ORDER_UPDATE」を通しのモデルケース**として、5ページ全体で
一貫した記入例を示す（実在のプロジェクト名称ではない、説明用のプレースホルダ）。実データは
[\[Sample\]NOUKI_PKG](<[Sample]NOUKI_PKG/index.md>)を参照。

**本ドキュメント種別はKCCSサンプルに直接対応する様式が存在しない（提案・未確定）。** 記入時は
その旨を踏まえ、既存の[\[Sample\]NOUKI_PKG](<[Sample]NOUKI_PKG/index.md>)の構成を
参考にしつつ、必要に応じて客先確認のうえ調整する。

**DB(SQL)処理IDについて**：**自己採番しない。** 実オブジェクト名（Oracleパッケージ／プロシージャー／
ファンクション名。例：`NOUKI_PKG`）をそのまま使う。6.4 DB(SQL)処理一覧の「オブジェクト名」列と
同じ値になる。

## 1. 設計書構成（index.md）

ファイル名は`{package-id}_01_cover.md`ではなく`index.md`とする（`cover`→`index`へ
改称。他の連番ファイルとは異なり番号・プレフィックスは付けない — mkdocsがフォルダーの入口ページとして
自動認識するのは正確に`index.md`という名前のファイルのみのため。画面設計書・バッチ処理定義書と
共通のルール）。従来ページ末尾に
あった「文書情報＋改定履歴」表（ファイル自体の改訂履歴）は削除する。「5. 設計書構成」直下には、
本オブジェクトで実際に作成したページに「作成」を、作成不要なページには「（対象外）」と記載する旨の
1文を置く（記入例は[Template]/[Sample]の`index.md`そのものを参照）。
「6. 改訂履歴（設計内容）」（オブジェクトの業務内容そのものの改訂履歴）とは
別物であり、これは維持する（両者を混同しないこと）。

**呼び出し元・戻り値の型は「オブジェクト概要」の1行ではなく、それぞれ独立した表**（「呼び出し元一覧」
「戻り値の型」）に記載する。呼び出し元は複数存在しうるため1呼び出し元＝1行とし、1セルに列挙しない。
複数のプロシージャー／ファンクションを持つパッケージでは、どの処理に対する呼び出しか・どの処理の
戻り値かを「呼び出すプロシージャー／ファンクション」「プロシージャー／ファンクション名」列で区別する。
オブジェクト種別がTRIGGERの場合は「呼び出し元一覧」を作成せず、「該当なし（発火元テーブル・イベント
は[インターフェース仕様](<[Template]{パッケージID}_{パッケージ名}/{パッケージID}_01_インターフェース仕様.md>)のトリガー発火条件を参照）」と記載する。

「オブジェクト概要」欄の記入例：

| 項目                         | 記載内容                                             |
| ---------------------------- | ----------------------------------------------------- |
| オブジェクト名               | PKG_ORDER_UPDATE                                      |
| DB(SQL)処理一覧No.           | 06章の[DB(SQL)処理一覧](<../../06-システム設計書（一覧、管理台帳）/6-4_DB(SQL)処理一覧/[Template]6-4_DB(SQL)処理一覧.md>)における該当行のNo.（オブジェクト名で検索して特定する。行アンカーは無いため、番号とスキーマ／オブジェクト名を併記して参照先を一意にする） |
| オブジェクト種別             | PACKAGE / PROCEDURE / FUNCTION / TRIGGER のいずれか   |
| 概要                         | このオブジェクトが何を行うかを1〜2行で                |
| 配置スキーマ                 | AZS                                                    |
| 作成者 / 作成日               | 氏名 / YYYY-MM-DD                                     |
| 更新者 / 更新日               | 氏名 / YYYY-MM-DD                                     |

「呼び出し元一覧」の記入例：

| No. | 呼び出し元種別 | 呼び出し元ID | 呼び出し元名 | 呼び出すプロシージャー／ファンクション | 呼び出し箇所 | 備考 |
| --- | -------------- | ------------ | ------------ | ------------------------------------ | ------------ | ---- |
| 1 | バッチ | BXXX001 | 受注日次取込バッチ | `PKG_ORDER_UPDATE.MAIN` | `BXXX001.sql` 内 `EXECUTE` 文 | － |
| 2 | 画面 | XXX111 | 受注登録 | `PKG_ORDER_UPDATE.UPD_ONE` | `OrderRegistServlet#doUpdate()` | － |

「戻り値の型」の記入例（FUNCTION以外は「該当なし」。複数のファンクションを持つパッケージでは、
ファンクションごとに1行で記載する。詳細な説明は[インターフェース仕様](<[Template]{パッケージID}_{パッケージ名}/{パッケージID}_01_インターフェース仕様.md>)
の「4. 戻り値」を参照）：

| No. | プロシージャー／ファンクション名 | 戻り値の型 | 桁数 | 概要 |
| --- | ------------------------------ | ---------- | ---- | ---- |
| 1 | `F_GET_STATUS` | NUMBER | 1 | 0:正常、それ以外:エラーコード |

「パッケージ内プロシージャー一覧」は、パッケージ内に複数のプロシージャー／ファンクションが存在する
場合のみ作成する。代表となる1本（呼び出し頻度が高い、または最も複雑なもの）を本ページ以降で
詳細化し、残りは本表に署名（引数の型のみ）を列挙するに留めてよい（詳細化は別途、客先確認のうえ
追加）。単独のプロシージャー／ファンクションのみのオブジェクトでは本節ごと削除する。

「5. 設計書構成」「6. 改訂履歴（設計内容）」は、バッチ処理定義書・画面設計書の
表紙と同じ位置づけ（設計書の索引ページ）。「5. 設計書構成」は、本オブジェクトで実際に作成した
ページに「作成」を、更新条件表・検索条件表のうちDB更新／検索を行わないため作成不要なページには
「（対象外）」と記載する。KCCS原本にある「上位文書」（標準設計書・共通設計書・ルール文書・
フロー設計書）は、Rikkei側から参照できず永久に「不明」のまま埋まらないため本サイトでは作らない
（画面設計書の表紙と同じ扱い）。

## 2. インターフェース仕様（{package-id}_01_interface-spec.md）

「基本情報」欄はバッチ・画面設計書と同様、システムID／DB(SQL)処理ID／オブジェクト名／作成日・
作成者を記載する（表紙と重複する項目だが、本ページ単独で参照された場合にも対象が特定できるようにする）。

**オブジェクト種別がTRIGGERの場合**：「引数定義」節は使わず、代わりに「トリガー発火条件」節を作成する
（PACKAGE／PROCEDURE／FUNCTIONの場合は逆に「トリガー発火条件」節を「該当なし（本オブジェクトは
{種別}のため対象外）」として残すか、節ごと削除する）。記入例：

| 項目               | 内容 |
| -------------------- | ---- |
| 対象テーブル         | T_ORDER                                    |
| 発火タイミング       | AFTER                                       |
| 対象イベント         | INSERT, UPDATE                              |
| 発火レベル           | 行レベル（FOR EACH ROW）                    |
| 発火条件（WHEN句）   | `NEW.STATUS <> OLD.STATUS`（UPDATE時のみ）  |

参照する`:NEW`／`:OLD`カラム：

| No. | カラム名 | `:NEW`参照 | `:OLD`参照 | 用途                       |
| --- | -------- | ---------- | ---------- | ---------------------------- |
| 1   | STATUS   | ○         | ○         | ステータス変更を検知して監査ログへ記録 |

**PACKAGE／PROCEDURE／FUNCTIONの場合**は以下「引数定義」を使う。パッケージ内に複数のプロシー
ジャ／ファンクションがある場合は、「プロシージャー／ファンクション名」列でどの処理の引数かを区別
し、同一表に続けて記載する：

引数定義：

| No. | 引数名     | IN/OUT/INOUT | 型       | 桁数 | 必須 | 説明                       |
| --- | ---------- | ------------ | -------- | ---- | ---- | -------------------------- |
| 1   | P_ORDER_ID | IN           | VARCHAR2 | 20   | ○   | 対象の注文ID               |
| 2   | P_RESULT_CD | OUT         | NUMBER   | 2    | -    | 処理結果コード（0:正常）   |

戻り値（FUNCTIONの場合。戻り値を持つ処理が複数ある場合は1処理＝1行で記載する。FUNCTIONが無い
場合は「該当なし」と記載する）：

| 型     | 説明                                     |
| ------ | ------------------------------------------ |
| NUMBER | 0=正常終了、1=業務エラー、9=システムエラー |

例外（EXCEPTION）定義：

| 例外名         | 発生条件                     | ハンドリング方針                                 |
| -------------- | ------------------------------ | --------------------------------------------------- |
| NO_DATA_FOUND  | 対象レコードが存在しない場合   | 呼び出し元にP_RESULT_CD=1を返却しRAISEしない        |
| OTHERS         | 想定外エラー                   | ログ出力の上RAISE、呼び出し元でロールバック         |

## 3. 処理概要（{package-id}_02_process-overview.md）

**「2. 処理フロー図」はMermaid flowchartで必ず作成する**（箇条書きでの代替は不可）。図は次の3点が
読み取れる粒度とする。

1. DB更新のノードに[更新条件表](<[Template]{パッケージID}_{パッケージ名}/{パッケージID}_03_更新条件表.md>)の`操作No.`を併記する。
2. DB検索のノードに[検索条件表](<[Template]{パッケージID}_{パッケージ名}/{パッケージID}_04_検索条件表.md>)の`検索条件表No.`を併記する。
3. `COMMIT`／`ROLLBACK`の実行箇所を独立したノードとして図中に明示する（コミットのタイミングは
   本図で表現し、「4. トランザクション方針」の表と併せて読めるようにする）。

「3. 処理ステップ（プロセス記述）」はバッチ処理定義書のプロセス記述書と同じ形式で、起動から終了まで
1行1ステップで記述する。

「基本情報」欄は上記2.と同じ値を記載する。

処理フロー概要は、箇条書きまたはMermaid flowchartで処理の流れを記述する。記入例：

> 1. 入力パラメーターの妥当性チェック → 2. 対象データのロック取得 → 3. 業務ロジック実行 →
> 4. 更新結果のコミット → 5. 結果コードの返却

「処理ステップ（プロセス記述）」は、バッチ処理定義書のプロセス記述書と同じ形式（No./処理内容/
入力/出力/備考）。処理フロー概要（自由記述の要約）を、実際にソースコードで追える単位（コミット
単位・ループ単位・呼び出し単位等）まで分解した表。記入例：

| No. | 処理内容                     | 入力                     | 出力                 | 備考           |
| --- | ------------------------------- | -------------------------- | ---------------------- | ---------------- |
| 1   | 入力パラメーターの妥当性チェック  | 引数`P_ORDER_ID`             | -                       |                  |
| 2   | 対象データの取得                | `TAZSA001_納期履歴`         | ローカル変数            | 検索条件表No.1参照 |
| 3   | 業務ロジック実行・結果反映      | 2の取得結果                 | `TAZSA001_納期履歴`（UPDATE） | 更新条件表No.1参照 |
| 4   | 結果コードを`P_RESULT_CD`に設定 | 3の実行結果                 | OUT引数`P_RESULT_CD`     |                  |

呼び出す他オブジェクト：

| No. | 呼び出し先オブジェクト         | 呼び出し目的       |
| --- | -------------------------------- | -------------------- |
| 1   | PKG_COMMON.F_GET_SEQ             | 採番取得              |
| 2   | PKG_ORDER_CHECK.P_VALIDATE       | 業務チェック実行      |

業務ルール・注意事項（自由記述）：

> 排他制御の方針、リトライ可否、トランザクション境界など、共通機能設計書や排他マトリクスと
> 矛盾しないよう記載する。

「異常時の挙動・リトライ／リカバリ方針」は、未捕捉の例外（[インターフェース仕様](<[Template]{パッケージID}_{パッケージ名}/{パッケージID}_01_インターフェース仕様.md>)
の例外定義でカバーされないエラー）が発生した場合の挙動、および再実行時の考え方を記載する。バッチ
処理定義書のチェック処理概要（終了コード／リトライ・通知方針／リラン・リカバリ）と同じ位置づけで、
DB更新の有無に関わらず全オブジェクトで作成する（更新条件表の「トランザクション方針」はコミット
単位・ロールバック範囲など更新固有の内容に絞り、本節は呼び出し元への通知方法・リトライ・再実行
手順など運用寄りの内容を扱う）。記入例：

| 項目                   | 内容 |
| ---------------------- | ---- |
| 正常終了時の通知方法   | OUT引数`P_RESULT_CD=0`を返却                          |
| 異常終了時の通知方法   | OUT引数`P_RESULT_CD`にエラーコードを設定、または例外をRAISEして呼び出し元に伝播 |
| 未捕捉例外発生時の挙動 | 呼び出し元のトランザクションはロールバックされる（本オブジェクト内でCOMMITしていないため） |

| 項目         | 内容                                     |
| ------------ | ------------------------------------------ |
| リトライ有無 | リトライなし（呼び出し元バッチのリトライ方針に従う） |
| 通知手段     | 呼び出し元のログ・通知機構に委譲             |
| 通知条件     | 該当なし（本オブジェクト自体は通知を行わない） |

| 項目                             | 内容                                         |
| -------------------------------- | ---------------------------------------------- |
| 再実行可否                       | 再実行可（COMMITしないため呼び出し元のロールバックで状態が戻る） |
| 再実行時の前提条件               | 特になし                                       |
| 処理途中で異常終了した場合の影響 | 呼び出し元のトランザクション境界内であれば影響なし |
| リカバリ手順                     | 呼び出し元の指示に従って再実行                 |

## 4. 更新条件表（{package-id}_03_update-condition-table.md）

- **スキーマ名とテーブル名は列を分ける**。`スキーマ.テーブル`の形で1セルに混ぜない。
- **更新種別**は`INSERT`／`UPDATE`／`DELETE`／`MERGE`／`TRUNCATE`から記載する。`MERGE`は一致時
  （UPDATE側）・不一致時（INSERT側）の設定内容を「3. 更新条件・更新項目」で分けて記載し、`TRUNCATE`は
  更新項目を「該当なし（全件削除）」とする。実装が「全件DELETE後にINSERT」の洗い替えの場合は
  `DELETE→INSERT`と記載してよい。
- **粒度は画面設計書の更新条件表と揃える**。「2. 更新概要」で操作を一覧化し、「3. 更新条件・更新項目」で
  操作No.ごとに更新条件（条件式）と更新項目（カラム一覧）を記載する。
- **更新項目を「ほか」「等」で省略しない**（設計書全体の共通ルール）。全件記載するか、構造的に網羅
  できない場合は理由を明記したうえで当該列自体を設けない。
- **コミットのタイミング**は「4. トランザクション方針」に加えて、[処理概要](<[Template]{パッケージID}_{パッケージ名}/{パッケージID}_02_処理概要.md>)
  の処理フロー図にCOMMITノードとして明示する。

DB更新を行わないオブジェクト（SELECTのみ等）では本ページを作成せず、表紙の「5. 設計書構成」で
「（対象外）」とする。

「基本情報」欄は上記2.と同じ値を記載する。

「更新条件」は**1テーブル・1操作を1行**とする（1項目を「、」「／」等で複数まとめない）。1オブ
ジェクトが複数テーブルを更新する場合はNo.を増やして列挙し、操作No.ごとに「3. 更新条件・更新項目」
のセクションを複製する。バッチ処理定義書の更新条件表と同じ列構成（テーブルID／テーブル名を分けて
記載し、接続先DBが複数スキーマにまたがる場合は必ず記載する）。記入例：

| No. | 更新種別      | 接続先DB／スキーマ | テーブルID | テーブル名                | 契機（処理フェーズ）       | 更新条件                                       | 更新項目       | 備考                                                     |
| --- | ------------- | ------------------- | ---------- | ----------------------------- | -------------------------- | ------------------------------------------------ | -------------- | -------------------------------------------------------- |
| 1   | UPDATE        | AZS                 | TAZSA001   | TAZSA001_納期履歴             | メイン処理中（業務ロジック実行後） | 注文ID一致かつステータス=処理中                  | ステータス     | 排他制御あり（排他マトリクス参照）                        |
| 2   | UPDATE        | AZS                 | TAZSA001   | TAZSA001_納期履歴             | No.1と同時                 | No.1と同一条件                                   | 更新日時       |                                                            |
| 3   | INSERT        | AZS                 | TZZJM003   | TZZJM003_出力履歴管理マスター | 処理完了時（後処理）        | 処理完了時に1件追加                              | 全項目         |                                                            |
| 4   | DELETE→INSERT | AZS                 | TWORK001   | ワーク_対象データ             | プロシージャー開始時（前処理） | 処理開始時に全件クリアしてから対象データを再抽出 | 全項目         | ステージング／ワークテーブルの洗い替えパターン            |
| 5   | UPDATE        | AZS                 | TAZSC010   | 共通設定マスター               | 処理完了時（後処理）        | 本処理の識別コードに該当する1件                  | 前回実行時刻   | 次回実行時の差分抽出条件として参照される（チェックポイント方式） |

操作No.ごとの更新条件は、WHERE句・MERGEのON句の条件を実際の条件式の形でコードブロックに記載する
（該当なしの場合は「該当なし（全件対象）」と明記する）。

「更新カラム詳細」は、更新条件だけでは追えないカラム単位の編集元・編集方法を、No.ごとに記載する
（未調査の場合は、テーブルを空欄で埋めるのではなく「未調査（理由）」と明記する）。記入例：

**No.1: TAZSA001_納期履歴のUPDATE**

| 項目   | 内容                           |
| ------ | ------------------------------- |
| 登録元 | 業務ロジックの処理結果           |

| No. | テーブル名           | カラム名 | 論理名 | 編集元         | 編集方法／補足         |
| --- | -------------------- | -------- | ------ | -------------- | ------------------------ |
| 1   | TAZSA001_納期履歴    | STATUS   | ステータス | 固定値       | "処理中" を設定          |

「トランザクション方針」の記入例：

| 項目                       | 内容                                             |
| -------------------------- | -------------------------------------------------- |
| コミット単位               | 呼び出し元（バッチ／画面）に委譲、本パッケージ内ではCOMMITしない |
| ロールバック範囲           | 本プロシージャーで行った全更新（呼び出し元のトランザクション境界に従う） |
| 異常終了時のデータ整合性   | 呼び出し元がROLLBACKすることで整合性を保つ         |
| 再実行時の重複登録防止キー | 注文ID＋処理日（一意制約あり）                     |

## 5. 検索条件表（{package-id}_04_search-condition-table.md）

DB検索を行わないオブジェクト（更新専用等）では本ページを作成せず、表紙の「5. 設計書構成」で
「（対象外）」とする。

「基本情報」欄は上記2.と同じ値を記載する。

画面設計書の検索条件表と同じ構成で、1テーブル・1検索条件を1行とする（1項目を「、」「／」等で
複数まとめない）。1オブジェクトから複数の検索が発生する場合は「検索条件表No.2」「検索条件表
No.3」…と検索単位ごとに複製する。「参照エンティティ一覧」でテーブルに記号（例：T=対象テーブル）
を振っておくと、各Noの表を簡潔に書ける。記入例：

**参照エンティティ一覧**

| 記号 | 内容               |
| ---- | ------------------ |
| T    | TAZSA001_納期履歴  |

**検索条件表 No.1**

| 項目 | 内容                             |
| ---- | ---------------------------------- |
| 概要 | 引数P_ORDER_IDに該当する納期履歴を取得 |
| 用途 | 業務ロジック実行前の対象データロード     |

検索条件：

| 検索対象テーブル | 演算子 | 条件項目名（参照先）     | 結合条件 | 必須 | 備考 |
| ------------------ | ------ | -------------------------- | -------- | ---- | ---- |
| T                  | =      | 注文ID = 引数P_ORDER_ID     | -        | 必須 |      |

結合条件・抽出条件は、無い場合はそれぞれ「該当なし」と記載する。ソート順は「更新日時 降順」の
ように記載し、取得件数・0件時の扱いまで明記する（「呼び出し元にP_RESULT_CD=1を返却」等）。
