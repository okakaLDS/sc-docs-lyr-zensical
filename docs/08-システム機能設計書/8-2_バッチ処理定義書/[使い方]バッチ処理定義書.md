# バッチ処理定義書 — 使い方

## 使い方

本ページは本フォルダー（`batch-processing-spec/`）配下の各テンプレートページ（01〜09）の
**書き方の指南**。04〜06系ドキュメントと同じく、[使い方]は[Template]／[Sample]と同じ階層
（本フォルダー直下）に置く。1バッチ＝1フォルダーに9ページ分かれるため、それら全ページ分の
記入例を本ページ1枚にまとめている（ファイル入出力・外部呼出等、該当しないページは作成不要）。

| フォルダー／ファイル | 位置づけ | 中身 |
| ------------------- | -------- | ---- |
| [\[Template\]{bat-name}](<[Template]{バッチファイル名}/index.md>) | 記入用の空テンプレート | 実データを持たない、ほぼ空のひな形（9ページ。処理フローとプロセス記述書は 1 ページに統合） |
| [\[Sample\]COMM_ftp](<[Sample]COMM_ftp/index.md>) | 実データ例（共通バッチエンジン） | FTPベースの共通バッチエンジン`COMM_ftp.bat`。「5. 呼出元一覧」に呼出元wrapper（`COMM_FTP_FVCC011`等）を記録する記入例 |
| [\[Sample\]COMM_FTP_FVCC011](<[Sample]COMM_FTP_FVCC011/index.md>) | 実データ例（薄いwrapper） | 本体ロジックを持たない2行の`.bat`。8項目中2項目のみ作成する記入例（0-5節） |
| [\[Sample\]goFVCC011](<[Sample]goFVCC011/index.md>) | 実データ例（wrapperから分離した実処理） | `COMM_FTP_FVCC011`から呼ばれる実処理本体。8項目とも作成する記入例 |
| **本ページ（\[使い方\]）** | 書き方の指南 | 各ページ・各項目の意味とプレースホルダによる記入例 |
| [使い方]（ベトナム語版） | 上記の翻訳版 | 旧版（{batch-id}表記）の翻訳のまま。本ドラフトの変更点は未反映（成果物本体は日本語で記入する） |

以下は**架空のバッチ「B001：注文実績日次集計バッチ」を通しのモデルケース**として、9ページ全体で
一貫した記入例を示す（実在のプロジェクト名称ではない、説明用のプレースホルダ）。実データは
[\[Sample\]goFVCC011](<[Sample]goFVCC011/index.md>)・[\[Sample\]COMM_ftp](<[Sample]COMM_ftp/index.md>)を参照。

## 0. ドキュメント化の単位・フォルダー作成基準（ドラフト新設）

### 0-0. ソースコードから抽出できる情報のみを記載する（xlsxに依存しない）

**本ドキュメントはソースコード（`.bat`／`.vbs`／`.wsf`／`.sql`／`.ctl`等）から抽出できる情報のみを
記載する。** Windowsタスクスケジューラの設定情報（`タスクスケジューラ一覧_納期管理_20260723.xlsx`）
に由来する内容（起動時刻・反復間隔・実行サーバー・実行ユーザ・「誰が呼ぶか」等）は、対象の`.bat`
ファイル自身のソースコードには含まれないため、**本書の内容としては記載しない**（該当する項目は
「対象外（本ファイルのソースコードからは特定不可）」と明記する）。

例外は次の1点のみ：**「フォルダー作成の要否（○／×／△）」の判定自体は、引き続きxlsxとの突き合わせで
行う**（0-3節）。これは「xlsxの内容を文書に書く」ことではなく、「その`.bat`が本番で実際に使われて
いるか」を確認するための作業であり、文書に残るのは判定結果（○／×／△）のみである。

理由：タスクスケジューラの設定はソースコードとは別に管理された外部の設定情報（一時点のエクスポート）
であり、ソースコードを起点に設計書を作成するという方針からは外れる。ソースコード側の実体は
`.bat`ファイルのみであるため、`.bat`ファイル自身から読み取れない情報は本書の対象外とする。

### 0-1. 「処理ID」＝ファイル名（.bat）とする

**`{bat-name}`は`.bat`ファイル名（拡張子を除いたもの）を指す**（例：`FVCC011`、
`COMM_FTP_FVCC011`、`goFVCC011`）。旧ドラフト（2026-09-02時点）では「タスクスケジューラ一覧の
実行するタスク列に現れる、またはエンジンに渡される引数」を処理IDとする案としていたが、その後の
社内レビューにより撤回した。理由：タスクという単位はソースコード自体の中では管理されておらず、
Windowsタスクスケジューラ側の設定（xlsx）にのみ存在する情報であるため、ソースコードを起点に
設計書を作成するという観点からは、外部の設定情報に依存しない`.bat`ファイル単位を単位とするのが
適切と判断した。

### 0-2. 1フォルダー＝1「.batファイル」

**1つの`.bat`（／`.vbs`／`.wsf`）ファイルにつき1フォルダーを作成する。** 1つのタスクが複数の独立した
`.bat`を一括起動している場合（例：タスク「納期管理_実績（FVCxx）の更新」が`COMM_FTP_FVCC007`〜
`015`の7本を一括起動）も、**タスク単位でまとめず、ファイルごとに別フォルダーとする**。

同一の`.bat`（／`.wsf`等）が複数の業務ID（引数）で繰り返し呼び出される場合（例：
`WebApi_Service.wsf VDRAD003` / `VDRAD004` / `VDRAM004`）は、そのファイル自体は1つの実体
（1フォルダー）とし、業務IDごとの違いは「8. 外部リクエスト仕様」の呼び出し一覧に
引数ごと1行で記載する（0-4節「共通バッチエンジン／パラメーター呼出しされる部品」参照）。

### 0-3. フォルダーを作成する条件

対象の`.bat`ファイルが次の**いずれか**に該当する場合のみ、`[Template]{bat-name}/`を
複製してフォルダーを作成する。判定自体はxlsxとの突き合わせで行うが、文書に残すのは判定結果のみとする
（0-0節参照）。

- (a) `タスクスケジューラ一覧_納期管理_20260723.xlsx`の実行するタスク列に直接記載されている
- (b) `sqlldr_lyr19-KCCS_*/`内の他ファイルから直接／動的（`go<ID>.bat`経由等）に呼び出されている

(a)(b)いずれにも該当しない場合はフォルダーを作成しない（0-6節参照）。

### 0-4. 共通バッチエンジン／パラメーター呼出しされる部品

以下5ファイルは、他の`.bat`から業務ID（引数）付きで繰り返し呼び出される共通部品である。
0-2節のとおり、これらも**他の`.bat`と同様に1ファイル＝1フォルダー**として扱う（旧ドラフトでは
「1タスク＝1フォルダー」ルールの例外として特別扱いしていたが、単位が`.batファイル`になったため、
特別扱いする理由が無くなった）。

| 種別 | エンジン | データ取得方式 |
|---|---|---|
| FTPベース | `COMM_ftp.bat`（主系） | FTP接続→取得→解凍→`go<ID>.bat`呼出 |
| | `COMM_ftp10.bat` | 別FTPサーバー向け |
| | `COMM_ftpSO.bat` | 別FTPサーバー向け |
| WebAPI/HTTPベース | `WebApi_Service.wsf`（主系） | HTTP取得→（gzip時）解凍→`go<ID>.bat`呼出 |
| | `postWebAPI.vbs` | 先行POST後、`go<ID>.bat`呼出 |

- 処理IDはファイル名そのまま（例：`COMM_ftp`、`WebApi_Service`）。
- 表紙の「バッチ分類」＝`共通バッチエンジン`とする（[バッチ一覧](<../../06-システム設計書（一覧、管理台帳）/6-3_バッチ一覧/[Template]6-3_バッチ一覧.md>)（6.3）の同列と一致させる）。
- `{bat-name}_08_external-request-spec.md`の「5. 呼出元一覧」に、本ファイルを引数付きで
  呼び出す**すべての呼出元**を1行ずつ記載する（呼出元のファイル名と渡される引数はソースコードから
  読み取れるため対象。ただし呼出元の起動タイミング・スケジュールはxlsx由来のため記載しない）。

### 0-5. 薄いwrapper（本体ロジックを持たないファイル）の扱い

例：`COMM_FTP_FVCC011.bat`（全内容が`call COMM_ftp.bat FVCC011`の1行のみ）。

- 0-2節のとおり、**このようなファイルも1ファイル＝1フォルダーとして扱う**（旧ドラフトでは
  「本体ロジックを持たないため専用フォルダーを作らず、呼出先エンジンの呼出元一覧に1行で記録する」
  としていたが、この方式では当該ファイル固有の内容（呼び出すエンジン・引数等）が、エンジン側の
  1つの表にしか残らず追跡しにくいため撤回した。実例：[\[Sample\]COMM_FTP_FVCC011](<[Sample]COMM_FTP_FVCC011/index.md>)参照）。
- ただし本体に固有ロジックが無いため、8項目のうち**該当する項目のみ作成**し、残りは表紙
  「2. 設計書構成」で「（対象外）」と明記する（作成不要な項目まで無理に埋めない）。目安：
  「1. 処理概要」「8. 外部リクエスト仕様」は作成、それ以外（チェック処理概要／DB取得仕様／
  更新条件表／ファイル入出力仕様等）は本体に該当ロジックが無いため対象外となることが多い
  （実例：[\[Sample\]COMM_FTP_FVCC011](<[Sample]COMM_FTP_FVCC011/index.md>)は8項目中2項目のみ作成）。
- 呼出し先の実処理（`go<ID>.bat`等）は**別ファイルとして別フォルダー**に作成する（実例：
  [\[Sample\]goFVCC011](<[Sample]goFVCC011/index.md>)）。

### 0-6. 対象外（未使用）の扱い

xlsxの実行するタスク列に**なく**、かつ他ファイルからも呼び出されていない（0-3節の条件(a)(b)いずれも
満たさない）場合：

- `batch-processing-spec/`にフォルダーを作成しない
- [システム機能一覧](<../../06-システム設計書（一覧、管理台帳）/6-1_システム機能一覧/[Template]6-1_システム機能一覧.md>)（6.1）の備考欄、および[バッチ一覧](<../../06-システム設計書（一覧、管理台帳）/6-3_バッチ一覧/[Template]6-3_バッチ一覧.md>)（6.3）の備考欄に`対象外（未使用）`と記載する
- 判定は現行ソース＋バッチファイルの参考情報（KCCS提供の参考Excel）の突合で行い、個別に運用担当への確認は行わない（バッチファイルの参考情報（KCCS提供の参考Excel）側が「使用中」に分類していても、本節の条件(a)(b)いずれも満たさなければ機械的に`対象外（未使用）`としてよいことはKCCS確認済み。0-7節参照。ただし機械的に判定したファイルの一覧は後でまとめてKCCS側へ共有し確認を受けること）

### 0-7. 運用担当への確認結果（2026-09-03 KCCS回答、AZR-418）

以下2件はバッチファイルの参考情報（KCCS提供の参考Excel）側で「使用中」（③）に分類されており、こちら側では
dead-code／孤立コードの疑いがあったため0-6節の`対象外（未使用）`を機械的に適用せず個別にKCCS確認を
依頼していたもの。回答が得られたため両件とも解決済み。

- `goVDRAD002.bat` … **現在は使用していない。テーブルVDRAD002も現環境に存在しない。** →
  `対象外（未使用）`として確定（[バッチ一覧](<../../06-システム設計書（一覧、管理台帳）/6-3_バッチ一覧/[Sample]6-3_バッチ一覧.md>)の
  `goVDRAD002`行を更新済み）。
- `kgss_seisan_up_cb52.bat` … **使用していると思われる**（タスクスケジューラを見る限り正常に稼働して
  いるため）。ただし実際にこのバッチでデータが更新されているかまでは未確認とのこと。→ 引き続き稼働中
  として扱う（フォルダー作成は維持。`rem`コメントアウト行の扱いは0-8節参照、これは未回答のため引き続き
  客先確認待ち）。

**今後の判定方針（KCCS回答）**：`goVDRAD002.bat`のように「ファイル実体はあるが、タスクスケジューラ
にも呼び出し先にも登場しない」場合は、今回のように個別に運用担当へ確認を仰がず、**一律で
`対象外（未使用）`と判断して問題ない**（0-6節の原則どおりでよく、本節のような個別確認は今後不要）。
ただし、そのように機械的に`対象外（未使用）`と判断したファイルの一覧は後でまとめてKCCS側へ共有し、
まとめて確認を受けること。

### 0-8. remでコメントアウトされた行が残るファイル

同一ファイル内の一部の行だけが`rem`でコメントアウトされ、他の行は現役の場合（例：
`kgss_seisan_up_cb52.bat`）、0-4節・0-6節のいずれにも該当せず**通常どおりフォルダーを作成**し、
現在有効な分岐のみを記述する。コメントアウトされた行のための専用項目は設けない。

## 共通の記入ルール

「ほか」「等」での省略禁止／1件＝1行／グループ化した行でもキー列を空欄にしない、の3点は [記述ルール 節10「列挙と行の書き方」](<../../05-システム設計書（全体）/5-9_標準設計書/5-9-1_記述ルール/[Sample]5-9-1_記述ルール.md#10-列挙と行の書き方一覧表の共通ルール>) を正とする（各ページに重複記載しない）。

## 1. 設計書構成（index.md）

表紙は**設計書の索引ページ**であり、技術情報は書かない（KCCSフォーマットの表紙シートに合わせた構成）。
記載するのは「1. バッチ概要」「2. 設計書構成」「3. 改訂履歴（設計内容）」の3つのみ。
起動方法・実行環境・終了コード等の技術情報は02／03／05へ記載する。

ファイル名は`{bat-name}_01_cover.md`ではなく`index.md`とする（`cover`→`index`へ
改称。他の連番ファイルとは異なり番号・プレフィックスは付けない — mkdocsがフォルダーの入口ページとして
自動認識するのは正確に`index.md`という名前のファイルのみのため。画面設計書・DB(SQL)処理定義書と
共通のルール）。従来ページ末尾にあった「文書情報＋改定履歴」表
（ファイル自体の改訂履歴）は削除する。「2. 設計書構成」直下には、本バッチで実際に作成したページに
「作成」を、作成不要なページには「（対象外）」と記載する旨の1文を置く（記入例は[Template]/[Sample]の
`index.md`そのものを参照）。「3. 改訂履歴（設計内容）」（バッチの業務内容そのものの
改訂履歴）とは別物であり、これは維持する（両者を混同しないこと）。

画面設計書の表紙にある「Ⅰ．上位文書」（標準設計書／共通設計書／ルール文書／フロー設計書への参照）は
本テンプレートには設けない。バッチ処理定義書は機能単位ではなくバッチ単位のフォルダー構成のため、
どのバッチの表紙も同じ4行を繰り返すだけの重複になり、バッチ固有の情報を持たないため。

「1. バッチ概要」欄の記入例：

| 項目            | 内容                                                                       |
| --------------- | -------------------------------------------------------------------------- |
| バッチ名        | 注文実績日次集計バッチ                                                     |
| バッチ分類      | 2. 実績集計（バッチ一覧の分類IDと分類名。共通バッチエンジンの場合は「共通バッチエンジン」と記載） |
| 概要            | 前日分の確定注文データを会社コード単位で集計し、集計結果テーブルへ登録するとともにCSVを出力する。 |
| 作成者 / 作成日 | 山田太郎 / 2026-07-16                                                      |
| 更新者 / 更新日 | 山田太郎 / 2026-08-20                                                      |

「2. 設計書構成」は、本バッチで**実際に作成したページに「作成」を、作成不要なページは「（対象外）」**と記載する（Customer／Developerのような区分は設けない。画面設計書と異なり、バッチ設計書のページはどれも社内の設計・開発情報であり、顧客提出可否での仕分けは不要）。
例えばファイル入出力を行わないバッチは、07／08の行を「（対象外）」とする。

**処理IDは自分で採番しない。**[バッチ一覧](<../../06-システム設計書（一覧、管理台帳）/6-3_バッチ一覧/[Template]6-3_バッチ一覧.md>)に
登録済みのIDをそのまま使う。**0-1節のとおり、処理ID＝`.bat`ファイル名（拡張子を除いたもの）**
とする（例：`FVCC011`、`COMM_FTP_FVCC011`、`goFVCC011`）。実ファイル名から拡張子を落とすと
別行の処理IDと衝突する場合（例：`.bat`ラッパーが呼び出す同名の`.py`本体）は、実体がスクリプトで
あることを明示する目的で拡張子を残してよい（例：`SeisanUpdate_new.py`）。


## 2. 処理概要（{bat-name}_01_process-overview.md）

「基本情報」「機能概要」「ファイルI/O」欄の記入例：

| ------------------ | ---------------------------- |
| システムID         | AZS                          |
| 処理ID             | B001                         |
| 機能名グループ     | 注文実績集計                 |
| 機能名（バッチ名） | 注文実績日次集計バッチ        |
| バッチ処理実行間隔 | 日次（毎日03:00実行）        |
| 作成日             | 2026-07-16                   |
| 作成者             | 山田太郎                     |

機能概要（自由記述）：

> 前日分の確定注文データを会社コード単位で集計し、集計結果を注文実績集計テーブルへ登録するとともに、
> 集計結果ファイルをCSV出力する。

ファイルI/O一覧：

| No. | ファイル名                     | I（入力） | O（出力） |
| --- | ------------------------------ | --------- | --------- |
| 1   | 注文実績日次集計ファイル(出力) |           | ●        |
| 2   | 注文実績連携ファイル(入力)     | ●        |           |

「起動・実行条件」欄の記入例（旧・表紙の「バッチ特有項目」から移設）。**起動時刻・反復間隔は
Windowsタスクスケジューラの設定情報＝xlsx由来であり、本ファイルのソースコードには含まれないため
記載しない**（0-0節参照）。記載するのは、本ファイル自身のソースコードから読み取れる項目のみ：

| 項目                     | 内容                                                                 |
| ------------------------ | -------------------------------------------------------------------- |
| 実行契機・パラメーター     | 前日分の注文実績データを対象。起動パラメーターで対象日付を指定可能（本ファイル自身が受け取る引数の扱い） |
| 多重起動の可否／排他制御 | 排他ファイル`goXXX.flg`の有無で判定。DBの状態フラグを併用する場合も記載（本ファイル自身のソースにフラグ操作コードがある場合のみ。呼出元／呼出し先が行う場合はその旨を明記し、詳細は当該ファイルのフォルダーを参照） |

「実行環境・前提」欄の記入例。**実行サーバー・実行ユーザはタスクスケジューラの設定情報であり、
本ファイルのソースコードから特定できないため対象外とする**：

| 項目                         | 内容                                                        |
| ---------------------------- | ----------------------------------------------------------- |
| 実行ディレクトリー             | `D:\scsales\sqlldr_lyr19\`（ソース内で`CD`する場合のみ。設定元が無ければ「未確認」） |
| 必要な環境変数               | `%LYR_SQLBAT_DIR%`（実行ディレクトリー）、`%LYR_SQLCONNECT%`（DB接続文字列） |
| 依存ミドルウェア・外部ツール | Oracle SQL*Plus、SQL*Loader、`ftp`コマンド、解凍ツール（共通バッチエンジンを経由する場合はそのエンジンのフォルダー名も記載）|

**環境変数はソースコードだけでは値が分からない**ことが多い。設定元（バッチ起動スクリプト・
システム環境変数）まで追えない場合は「未確認」と明記する。

**「5. データベース CRUD」にはCRUD表そのものを書かない。** バッチ単体のCRUD表を各設計書に持たせると、
呼び出し先（DB(SQL)処理等）での更新を含めた全体像が二重管理になるため、CRUDは
`05-system-design-overall/CRUD表`（5.5 CRUD表）に一元管理し、本ページからは参照先（ファイル名と
対象処理ID）のみを記載する。Markdownでは他ファイルの特定行へリンクできないため、リンクではなく
「どのファイルの、どの処理IDの行を見ればよいか」を文章で示す。


## 3. 処理フロー（{bat-name}_02_process-flow.md。処理ステップ（プロセス記述）を含む）

Mermaidのflowchartで「起動→前提条件チェック→対象データ抽出→0件判定→主処理→エラー判定→
結果出力→正常終了」の分岐を図示する（テンプレートのMermaid図はこのまま流用可）。

「実行順序（ジョブネット）」には、**本ファイル自身のソースコードから読み取れる**前後関係
（本ファイルが他の`.bat`を`call`する、または本ファイルが呼出元から`call`される等）を記載する。
同一タスクから起動される他バッチとの前後関係はWindowsタスクスケジューラの設定情報であり、
本ファイルのソースコードには含まれないため記載しない（0-0節参照）。呼出し関係が無ければ
「該当なし」。

「実行順序（ジョブネット）」は、本バッチが `.bat` の連鎖のどこに位置するか（先行／本バッチ／後続）の**概要**だけを書く。対象は `.bat` のみで、API・DB(SQL) 処理は現れない。引数・接続先はここに書かず、後続の詳細は「外部リクエスト仕様」の「3. 呼び出し一覧」「4. 引数」、先行の詳細は同「5. 呼出元一覧」を参照する（二重管理しない）。

「補足」には、フロー図では表現しきれない設計上の前提・制約を箇条書きで記載する。不要なら節ごと削除する。

「処理ステップ（プロセス記述）」には、処理ステップを起動から終了まで 1 行 1 ステップで記述する（旧「プロセス記述書」
`{bat-name}_03_process-description.md` を本ページに統合。AZR-418 ④）。`No.` はフロー図のノードと対応させる。記入例：

| No. | 処理内容                                                     | 入力                 | 出力                               | 備考                                            |
| --- | ------------------------------------------------------------ | -------------------- | ---------------------------------- | ----------------------------------------------- |
| 1   | 起動パラメーター（対象日付）を取得する                         | 起動パラメーター       |                                    |                                                 |
| 2   | 注文実績テーブルから対象日付の確定注文データを抽出する       | 注文実績テーブル     | ワークデータ                       | DB取得仕様参照         |
| 3   | 会社コード単位に件数・金額を集計する                         | ワークデータ         | 集計結果（メモリー／ワークテーブル） |                                                 |
| 4   | 集計結果を注文実績集計テーブルへ登録する                     | 集計結果             | 注文実績集計テーブル               | 更新条件表参照 |
| 5   | 集計結果をCSVファイルへ出力する                              | 注文実績集計テーブル | 注文実績日次集計ファイル(出力)     | ファイル出力仕様参照 |
| 6   | 処理結果をログに出力し、正常終了する                         |                      | ログ                               |                                                 |

## 4. チェック処理概要（{bat-name}_03_check-process-overview.md）

「基本情報」欄はバッチ共通（表紙・処理概要と同じ値）。チェック項目の記入例：

| No. | チェック項目             | 区分     | チェック内容・経緯                             | レベル     | 出力先                   | 異常時の内容／対応                                                       |
| --- | ------------------------ | -------- | ----------------------------------------------- | ---------- | ------------------------ | -------------------------------------------------------------------------- |
| 1   | 入力ファイル存在チェック | 前処理   | 対象の入力ファイルが所定のフォルダーに存在するか  | エラー     | ログ                     | ファイルが存在しないため異常終了する。                                     |
| 2   | 件数チェック             | 前処理   | 入力ファイルの件数が0件でないか                 | エラー     | ログ                     | 処理対象データが0件のため異常終了する。                                    |
| 3   | マスター存在チェック       | 処理中   | 参照先マスターにキーが存在するか                  | ワーニング | ログ／エラー一覧ファイル | 該当マスターが存在しないデータはスキップし、エラー一覧ファイルへ出力する。   |
| 4   | 排他チェック             | 前処理   | 同一バッチが多重起動されていないか              | エラー     | ログ                     | 多重起動を検知したため異常終了する。                                       |

凡例：

- レベルが「エラー」の場合は原則としてバッチを異常終了とし、後続処理を実行しない。
- レベルが「ワーニング」の場合は処理を継続し、対象データのスキップやエラー一覧ファイルへの出力など、バッチごとの方針に応じた扱いとする。

「終了コード」には、バッチが呼び出し元へ返す終了コードとその意味を記載する。
**バッチ内部で終了コードを判定していない場合は、その事実自体を記載する**（後続処理が異常を
検知できない構成であることが分かるため）。

| 終了コード | 意味                     | 後続処理の扱い                       |
| ---------- | ------------------------ | ------------------------------------- |
| 0          | 正常終了                 | 後続バッチを実行する                 |
| 8          | 入力データ不正で異常終了 | 後続バッチを実行せずジョブを中断する |

「異常終了時のリトライ／通知方針」「リラン（再実行）／リカバリ」の記入例：

| 項目         | 内容                                     |
| ------------ | ---------------------------------------- |
| リトライ有無 | リトライ3回（5分間隔）                   |
| 通知手段     | 運用担当（ops@example.com）へメール通知  |
| 通知条件     | 3回失敗時、および入力ファイル未着時      |

| 項目                             | 内容                                                       |
| -------------------------------- | ---------------------------------------------------------- |
| 再実行可否                       | 再実行可                                                   |
| 再実行時の前提条件               | 当日分の集計結果を削除してから再実行する                   |
| 処理途中で異常終了した場合の影響 | 集計テーブルに中途半端なデータが残る                       |
| リカバリ手順                     | 集計テーブルの当日分を削除後、対象日付を指定して再実行する |
