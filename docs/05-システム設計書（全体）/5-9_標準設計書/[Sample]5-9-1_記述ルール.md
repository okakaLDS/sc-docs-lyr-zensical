# 標準設計書 — 記述ルール

/// tab | 本文


*設計書を書くときの表記の決まり。ここで決めておけば、各設計書で毎回書かずに済む。
標準設計書の全体像・文書情報は index を参照。*

> **📌 前提：本設計書は Markdown で作成し、生成AIの入力にも使う**
>
> *本プロジェクトの設計書は Excel ではなく **Markdown** で作成する。
> 保守工程で**生成AI（Copilot／Gemini／Claude 等）に読ませ、影響調査に活用する**前提があるため、
> 以下のルールは「人が読みやすいか」だけでなく「機械が正しく解釈できるか」も基準にしている。*
>
> *リポジトリのフォルダー構成・ファイル名規則など作業環境側の取り決めは `template-list.md` を参照。*

## 1. ドキュメントの構成

| No. | 項目 | ルール |
| --- | ---- | ------ |
| 1 | ファイル分割 | **1ドキュメント＝1ファイル**。ファイル名は `{項番}_{ドキュメント名}.md`（例：`6-7_DB一覧.md`）。テンプレート／使い方／サンプルに分ける場合は、`{項番}_{ドキュメント名}/` フォルダーに `[Template]{項番}_{ドキュメント名}.md` `[使い方]…` `[Sample]…` を置く（例：`[Sample]6-1_システム機能一覧.md`）。実体ごとに 1 ファイルになる様式（4.2 共通機能処理概要・7.1・7.2・8 章）は `[Template]{ID}_{名称}.md` のように実体名で命名し、項番はフォルダー名で持つ |
| 2 | ファイル名の理由 | 同名ファイルが多数あると、生成AIに読ませたときにどの文書か特定できないため |
| 3 | 先頭 | `# {ドキュメント名}` の見出しに続けて**本体（設計内容）**を置く。文書情報は先頭に置かず末尾にまとめる（No.5） |
| 4 | 文書情報 | 大分類／小分類／ドキュメント名／システムID／システム名 の**5列**で統一（末尾に置く）。日付・担当・計画書No.・課題No. は改定履歴に一本化（二重管理を避ける）。大分類＝章番号・小分類＝doc_no。※KCCS/ベンダー作成分の遡及は別途 |
| 5 | 文書情報・改定履歴の位置 | **ファイル末尾に「文書管理ブロック」としてまとめる**（`## 文書情報` の直後に `## 改定履歴`）。Sample・Template・使い方のいずれも持つ（索引の `index.md` は No.11）。文書情報・履歴は設計内容と同格に先頭へ置かない（AIが最初に読むのが設計内容になるようにするため）。`## 改定履歴` は最末尾に置く。**例外：表紙（項番1）のみ文書情報を冒頭に置く**（表紙は文書そのものの識別が主目的のため。改定履歴は表紙も末尾） |
| 6 | front matter | `title` / `tags` / `status` / `doc_no` / `owner` を必ず記載する |
| 7 | `status` の値 | `作業中` / `承認済` の2値（承認済＝承認・捺印済みの版）。必ず最新にする。**`status` はレビュー工程で利用する項目で、ドキュメント作成完了時（正式版化）に削除する＝最終版には残らない**（SC様と合意、AZRK-22。正式版スナップショットでは自動で除かれる）。**テンプレート・記入例など実データでないファイルは `status` ではなくファイル名（`[Template]`/`[使い方]`/`[Sample]`/`_vi`）で判別**し、AI入力時に除外する |
| 8 | 見出し番号 | `## 2.` `### 2-1.` の形式。章が増えたら番号を振り直す |
| 9 | ドキュメントの分割 | 1ファイルが長大になる場合はフォルダー化し、`index.md` に全体像（一覧・索引）を置いて配下に分割する |
| 10 | 改定履歴の列 | 全ドキュメント共通で `Version｜計画書No.｜改訂日｜改訂内容｜担当者｜課題No./備考` の6列に統一する。承認情報・署名済みPDFの保管先は必要に応じて「課題No./備考」へ注記（表紙の改定履歴は基本設計書ぜんたいの版管理を兼ねる） |
| 11 | フォルダー入口 `index.md` | 機能ID／バッチID／パッケージID単位のフォルダーの入口 `index.md`（旧・表紙）は**索引ページ**のため、文書情報・改定履歴（ファイル自体の履歴）を持たない。その機能の設計内容の改訂は `index.md` 内の「Ⅱ．改訂履歴（設計内容）」に積む。「改訂履歴（設計内容）」（見出しは算用数字。画面 5.／バッチ 3.／DB(SQL) 6.）の列も No.10 と同じ 6 列（Version｜計画書No.｜改訂日｜改訂内容｜担当者｜課題No./備考）に統一する（2026-09-11。ベンダー納品の 5 列形式は 6 列に直す）。画面設計書では「関連画面一覧」「関連帳票一覧」も `index.md` 側に置く（2026-09-03 ベンダー提案を採用） |

## 2. Markdownの記法

*VSCode のプレビューと mkdocs の両方で同じように読めることを条件とする。
レビューは `.md` 単体で行うため、**片方でしか描画されない記法は使わない**。*

| 使ってはいけない記法 | 理由 | 代わりに |
| -------------------- | ---- | -------- |
| `=== "本文"`（タブ記法） | 4スペース字下げを要求するため、VSCode ではコードブロックになり表が読めない | 素の見出し `## 本文` |
| `!!! note` / `??? note`（admonition） | 同上。中の表が壊れる | 引用ブロック `> **📌 見出し**` |
| `<details>`（`markdown="1"` なし） | mkdocs 側で中の表がパイプ記号のまま出る | `<details markdown="1">` |
| リンク先にスペース | `](../4-2 共通機能処理概要/…)` は両方で壊れる | パスにスペースを使わない。やむを得ない場合は `](<...>)` |
| 画像だけの図 | 生成AIが内容を読めず、影響調査に使えない | Mermaid（節3） |

| 使ってよい記法 | 用途 |
| -------------- | ---- |
| `> **📌 見出し**` | 補足・注意事項 |
| `<details markdown="1">` | 常時表示が不要な補足（検索用の明細など）を折りたたむ |
| `<br>` | 表のセル内改行 |
| ` ``` ` | SQL・ファイル例などのコードブロック |

## 3. 図の書き方

*図はすべて **Mermaid** で記述する。画像は原則使わない（テキストなら差分が追え、生成AIも内容を読める）。*

| 図の種類 | 使う記法 | 理由 |
| -------- | -------- | ---- |
| 業務フロー | `sequenceDiagram` | 担当者が縦レーンとして固定される。`flowchart` の `subgraph` は自動レイアウトのため配置が崩れる |
| 画面遷移・オペレーションフロー | `flowchart` | 分岐や戻りを自然に表現できる |
| システム関連図 | `flowchart` | 連携の向きと種別を線種で描き分けられる |
| ER図 | `erDiagram` | 複合キーは `PK, FK` と書く（`PK_FK` は構文エラー） |
| タイムチャート | `gantt` | |

| No. | 対象 | ルール |
| --- | ---- | ------ |
| 1 | `flowchart` | **起点と終点を明示する**。`([業務開始：〜])` `([業務完了：〜])` の角丸ノードを置く |
| 2 | `flowchart` | **主フローを太矢印（`==>`）、副次的な遷移を細矢印（`-->`）**にする。太矢印だけを追えば順路がたどれる状態を保つ |
| 3 | 共通 | 矢印にはラベルを付ける（アクション名・データ名・ファイルIDなど） |
| 4 | 共通 | 図に凡例を添える。記号だけでは意味が確定しないため |
| 5 | 共通 | 図と同じ内容を**表でも書く**（節4の「明細」参照）。図はレイアウトが自動で順序が保証されないため。**例外：一度作成した後に変わらない説明図（2.1 システム化の背景・目的の導入前フロー等）は図だけでよい。設計の正となる図（業務フロー・画面遷移・CRUD 等）は表を省かない** |
| 6 | `sequenceDiagram` | 組織は `box` で色分け、工程は `Note over` で「① 工程名」と番号付き、ステップは `autonumber`、処理中は `activate`／`deactivate` で示す。起点・終点は工程①と最終工程の `Note` で示す（角丸ノードは使わない）。矢印は実線 `->>`＝依頼・実行、破線 `-->>`＝応答・戻り、開矢印 `-)`＝非同期、`-x`＝失敗・中断。記法サンプルと詳細は [3.1 業務フローの使い方](<../../03-業務設計書/[Sample]3-1_業務フロー.md>) |

## 4. 表の書き方

| No. | ルール |
| --- | ------ |
| 1 | 記号（`●` `○` `×` `－` 等）を使う表には、**必ず凡例を付ける** |
| 2 | 「該当なし」は空欄にせず `-`（ハイフン）を明示する。**記入漏れと区別する**ため（全角 `－` でも可・全半角は統一しなくてよい） |
| 3 | 数値・IDは全角にしない。IDは `` `TAZSD001` `` のようにコードスパンで囲む（ただし文書情報欄のシステムID等は対象外） |
| 4 | セル内で改行したい場合は `<br>` を使う |

> **📌 マトリクス（行列）には検索用の明細を併記する**
>
> *行×列の交点に記号を置くマトリクス形式は、列が多いと
> 「その記号がどの列のものか」を数える必要が生じ、人もAIも取り違える。
> 該当する表には、同じ内容を**「1行＝1組み合わせ」に展開した明細**を
> `<details markdown="1">` で折りたたんで併記する。*
>
> | 判断基準 | 明細の要否 |
> | -------- | ---------- |
> | 列が10を超える、または空白が大半を占める | **必要**（例：CRUD表は85列・充填率8.3%） |
> | 列が数個で、ほぼ全マスが埋まる | 不要（例：メニュー構成表は6列・ほぼ全マス） |
>
> *明細では記号だけでなく**意味の文言も併記**する。
> 1行を切り出したときに凡例なしで読めるようにするため。
> マトリクスを更新したら明細も必ず同時に更新すること。*

## 5. 用語・表記

| No. | ルール |
| --- | ------ |
| 1 | **半角カナを使わない**（`ﾌｧｲﾙ` → `ファイル`）。「ファイル」で検索しても `ﾌｧｲﾙ` はヒットせず、影響調査で漏れるため |
| 2 | ただし**実在するファイル名・シート名はコードスパン内に原文のまま残す**（`` `Ⅳ-9.標準設計書.xlsm` ``）。全角化すると参照先が存在しなくなる |
| 3 | 業務用語は [用語集](<../../03-業務設計書/[Sample]3-3_用語集.md>) に登録し、初出はリンクする |
| 4 | ID（画面ID・テーブルID・機能ID・ファイルID）は表記を1つに固定し、別名を作らない |
| 5 | 記入すべき箇所は `（記入）`、可変部分は `{画面ID}` のように示す |
| 6 | 他ドキュメントの内容を転記せず、リンクで参照する。二重管理を避けるため |
| 7 | **文体は「である調」（常体）で統一する**。設計書・要件定義書・入口ページ・使い方とも同じ。ただし画面のメッセージやエラー文言の引用（「〜してください。」等）はそのまま書き、SC様への依頼文も文書の性質に合わせてよい |

## 7. ファイル出力の書き方

*桁数・端数処理・日付形式など、ファイル出力仕様を書くときの共通の決まり。
「特別明記がない限りこの編集内容とする」というデフォルトを定めておくと、

| No. | 項目 | ルール |
| --- | ---- | ------ |

## 8. 版数（Ver.）の付番ルール

*設計書の版数の付け方。全注の原本には「Ver採番ルール」シートがあった。本プロジェクト用の仮置きで、実運用に合わせて確定する。
（表紙（項番1）から移設。2026-08-19）*

**版数は2階層で管理する（混同しない）**

| 対象 | どこで管理 | 例 |
| ---- | ---------- | -- |
| システム全体の基本設計書 | 表紙（項番1）の改定履歴（表紙の改定履歴が全体版管理を兼ねる） | `Ver. 1.0.0` |
| 各ドキュメント個別 | 各ファイル末尾の「改定履歴」 | `1.0` / `1.1` |

**全体版数（X.Y.Z）の桁の上げ方**

| 桁 | 例 | 上げるタイミング |
| ---- | ---- | ---- |
| メジャー（X） | **1**.0.0 | フェーズ完了・大規模な構成変更 |
| マイナー（Y） | 1.**1**.0 | ドキュメントの新規追加・章単位の改訂 |
| パッチ（Z） | 1.0.**1** | 誤記修正・軽微な内容反映 |

## 9. 承認・捺印の運用

*基本設計書の承認（捺印）の進め方。表紙（項番1）から移設（2026-08-19）。
承認された正＝「表紙をPDF印刷し、そのPDFに捺印したもの」とする。
生きたMarkdownには印影を貼らず、承認の記録（表紙の改定履歴）だけを持たせる
（生きた文書に印影を貼っても、版が変わると「別内容への承認」となり証跡が無効になるため）。*

| 手順 | 作業 | 補足 |
| ---- | ---- | ---- |
| 1 | Markdownで作成・レビュー | 生きた版（AI可読・版管理） |
| 2 | 承認する版を凍結 | 版数を確定し、その時点を保存（アーカイブ／版数を表紙の改訂履歴に記録） |
| 3 | 表紙を**PDF印刷** | ブラウザーで表紙を開き、印刷（Ctrl+P）→「PDFに保存」。押印枠が出た状態で出力する |
| 4 | PDFに**捺印** | 表紙の押印枠に、承認者ごとに捺印（電子印鑑を貼付、または印刷して押印しスキャン） |
| 5 | 署名済みPDFを**社内保管** | SharePoint／SVN等。**Public GitHubには置かない**（個人情報・なりすまし防止） |
| 6 | 表紙の改定履歴に記録 | 版数・改訂日・改訂内容を追記。署名済みPDFは社内保管とし、必要なら保管先・承認情報を「課題No./備考」に注記 |

> **📌 PDF印刷の注意**
>
> *・押印枠は表紙のCSS（`docs/stylesheets/extra.css` の `.seal-box`）で描画している。
> **VSCodeプレビューからPDF化すると枠が出ない**ため、印刷はビルドしたサイト
> （`mkdocs serve` のローカルプレビュー、または公開サイト）の表紙ページから行う。*
>
> *・電子印鑑をPDFに貼るにはPDF編集ソフト（Acrobat等）が要る。
> 紙に印刷して物理捺印→スキャンでもよい。印影ツールはImprintX等を想定。*

## 10. 列挙と行の書き方（一覧・表の共通ルール）

*ベンダー納品の各「使い方」に同文で記載されていた共通ルールを、本書に一本化した（2026-09-03）。各「使い方」からは本節を参照する。*

| No. | ルール | 内容 |
| --- | ------ | ---- |

| 2 | **1件＝1行** | 対象が複数ある場合、1つの行・セルにカンマ区切りや箇条書きでまとめない。**対象ごとに行を分けて全件を記載**する（例：1機能が複数の帳票を出力する場合は1帳票＝1行、1つのDB処理を複数の画面・バッチが呼ぶ場合は呼び出し元1件＝1行、更新条件表は1テーブル・1操作＝1行） |
| 3 | **グループ化した行でもキー列を空欄にしない** | Excelの縦方向セル結合に相当する見た目を再現するために、先頭行以外のキー列を空欄にすることは禁止。1つの親に複数行が紐づく一覧・マトリクス表では、**グルーピングのキー列を全行に同じ値で繰り返し記入**する（空欄だと検索・フィルタで拾えず、行単位の突合ができない） |

## 11. ID体系（リバース案件での採番方針）
