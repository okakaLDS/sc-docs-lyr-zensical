# 機器選定条件 — サンプル（記入例）

*記入イメージの例であり、実データではない。空テンプレートは 空テンプレート、前提は 使い方 を参照。
本例は**リバース案件**を想定した記入例。新規の調達方針は策定せず（現行流用）、負荷条件は現行システムを調査した実測値で表す。*

## 1. 調達方針

*リバース案件のため、新規の調達方針は策定しない（現行機器を流用する）。*

| 項目 | 方針 |
| ---- | ---- |
| 調達区分 | 現行機の流用 |
| 現行構成の扱い | 現行構成をそのまま踏襲する（変更点のみ本設計で定義） |
| 判断の理由 | リバース案件のため。新インフラの調達・方針策定は行わず、現行機器・現行構成を前提とする |

## 2. 選定条件

| No. | 区分 | 条件 | 根拠 | 備考 |
| --- | ---- | ---- | ---- | ---- |
| 1 | 性能 | 現行構成に準拠 | 負荷条件（節3）を満たすこと | 現行流用のため新規の性能設計は行わない |
| 2 | 可用性 | 現行構成に準拠 | 運用時間（運用方針）を満たすこと | |
| 3 | 保守 | EOL/EOS が稼働予定期間をカバー | 保守切れの持ち込みを防ぐ | 現行のOS/DBバージョンの保守期限を調査して確認 |

## 3. 前提とする負荷条件

*リバース案件のため、想定値は新規に設計せず、現行システムを調査した実測値を記載する。*

| 項目 | 想定値 | 備考 |
| ---- | ------ | ---- |
| 同時接続ユーザー数 | 50（現行調査） | 現行システムの実測（ピーク時） |
| ピーク時トランザクション数 | 100 tps（現行調査） | 現行システムの実測 |
| データ増加量（年間） | 約200MB（現行調査） | 現行DBの増加実績。開発方針のデータ増加量と整合 |
| ディスク使用量の見込み | 現行実績＋余裕分 | 現行の使用量を調査し、保存期間から算出 |

## 4. 導入の経緯・インフラ構成の変遷

*（例）本システムの基盤を選定した経緯と、導入後の構成の変遷。*

### 4-1. プラットフォーム選定の経緯

- （例）選定は社内のシステム委員会で決定した。選定条件は「Web 系で開発する」「個人開発ではなく委員会として保守できる」の 2 点。
- （例）上記を満たす製品として、ベンダー提案のアプリケーション基盤を採用した。

### 4-2. インフラ構成の変遷

| 時期 | 構成 |
| ---- | ---- |
| 2006年 | AP サーバー × 2、DB サーバー × 2（クラスター構成） |
| 2011年 | AP × 1（Active＋Standby）、DB × 1（Active＋Standby）に縮小（投資抑制） |
| 2018年 | 仮想環境へ移行 |
