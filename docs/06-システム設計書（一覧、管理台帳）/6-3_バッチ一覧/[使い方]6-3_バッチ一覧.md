# バッチ一覧 — 使い方

## 使い方

本ドキュメント（6.3 バッチ一覧）は用途別に3ファイルへ分けて管理する。

| ファイル | 位置づけ | 中身 |
| -------- | -------- | ---- |
| [\[Template\]batch-list](<[Template]6-3_バッチ一覧.md>) | 記入用の空テンプレート | 実データを持たない、ほぼ空のひな形 |
| [\[Sample\]バッチ一覧](<[Sample]6-3_バッチ一覧.md>) | 実データ例 | SC納期管理（`lyr07-KCCS`）の調査結果を記入した記入例 |
| **本ページ（\[使い方\]）** | 書き方の指南 | 各項目の意味・記入基準の解説 |

*項番6.3は暫定（SC様と調整中）。*

## ドラフトでの変更点（1件＝1「.batファイル」への変更）

`AZR-418`の課題整理を受け、一旦「タスクスケジューラ一覧上の処理ID（タスクに渡される引数／業務ID）」を
主キーとする案を検討したが、その後の社内レビューにより**1行＝1「.batファイル」**の方式へ確定した
（タスクは実体がソースコード外＝Windowsタスクスケジューラの設定にのみ存在し、ソースコード上の実体は
`.bat`ファイルのみであるため）。詳細な判定ルール（フォルダー作成基準・共通バッチエンジン・薄いwrapper・
対象外（未使用）の切り分け）は[\[使い方\]バッチ処理定義書](<../../08-システム機能設計書/8-2_バッチ処理定義書/[使い方]バッチ処理定義書.md>)の「0. ドキュメント化の単位・フォルダー作成基準」に一本化し、
本ページでは重複説明しない。本ページで変更するのは次の点。

- 列名「バッチID」→「バッチファイル名」（下記「1. バッチ一覧」の項目説明を参照。`.bat`ファイル名から
  拡張子を除いたものと一致。一時「処理ID」という列名も検討したが、「処理」という語が
  タスク／業務単位を連想させ紛らわしいため、実体どおり「バッチファイル名」とした）
- 「参照エンジン（該当時）」列を新設（下記参照）
- 備考欄の`未使用`は`対象外（未使用）`に表記統一（08側の呼称と合わせる）
- 「実行条件」「周期」列を削除（Windowsタスクスケジューラの設定情報＝xlsxに由来する内容であり、
  ソースコードから抽出できる情報のみを記載する方針としたため。0節参照）。**実行条件・周期（タスクスケジューラ由来の運用情報）は 9.2 タイムチャート（運用設計・SC様担当）で持つ**（KCCS 判断 2026-09-06。旧 6.3 の値は `記録/9-2タイムチャート材料_旧6.3実行条件・周期.md` に退避）
- 薄いラッパーも`フォルダ作成＝○`とする（旧`×`扱いを廃止。0-3節・「フォルダー作成」の項目説明参照）

## 共通の記入ルール

「ほか」「等」での省略禁止／1件＝1行／グループ化した行でもキー列を空欄にしない、の3点は [記述ルール 節10「列挙と行の書き方」](<../../05-システム設計書（全体）/5-9_標準設計書/5-9-1_記述ルール/[Sample]5-9-1_記述ルール.md#10-列挙と行の書き方一覧表の共通ルール>) を正とする（各ページに重複記載しない）。

## 0. 記載範囲についての方針（xlsxに依存しない・全件記載）

本一覧はソースコードから抽出できる情報のみを記載し、Windowsタスクスケジューラの設定情報
（`タスクスケジューラ一覧_納期管理.xlsx`）に由来する起動時刻・反復間隔等の**内容**は記載しない
（旧「実行条件」「周期」列は削除。詳細は[使い方]バッチ処理定義書.md「0. ドキュメント化の単位」参照）。

**ソースコード内に実在する`.bat`（／`.vbs`／`.wsf`）ファイルには、使用実態の確認有無にかかわらず
すべて設計書を作成する。** そのため本一覧も、実在する全ファイルを1行＝1ファイルで記載する
（旧版にあった「フォルダー作成の要否（○／×／△）」判定・列は廃止。xlsxとの突き合わせによる
使用実態の判定は、設計書作成の可否を決めるゲートとしては使わない。ただし調査で判明した使用実態
〈対象外（未使用）と思われる／未確認〉は、参考情報として「備考」欄に残す）。

## 1. バッチ一覧

**サンプル様式**

| No. | バッチ分類 | バッチファイル名 | 処理概要 | 参照エンジン（該当時） | 備考 |
| --- | -------- | -------- | -------- | ---- | ---- |
| 1   | FTP Flow | BATCH_NAME | `COMM_ftp`を呼ぶ薄いラッパー（固有ロジックなし）。 | COMM_ftp |  |
| 2   | FTP Flow | BATCH_NAME2 | 単独で固有のDBロード・更新処理を行う。 |  |  |
| 3   | FTP Flow | BATCH_NAME3 | | | タスクスケジューラに対応するタスクなし。使用実態は不明だが、ソースが存在するためspecは作成する |
| 4   | 共通バッチエンジン | COMM_ftp | BATCH_NAME等の薄いラッパーから呼ばれる共通部品。 |  |  |

*各項目の意味と記入内容：*

- ***No.*** … 1から連番（欠番なし）。分類（バッチ分類）をまたいでも途切れない1本の連番で、
  分類ごとに採番し直す番号ではない。**表の最後（最大）の番号＝実際に作成するフォルダーの総数**
  であり、各番号の行の「バッチファイル名」がそのままフォルダー名になる。行が増減した場合は
  全体を振り直す。
- ***バッチ分類*** … 見積書（詳細設計）「見積明細書（詳細設計）」シートの`カテゴリ`列の値
  （`FTP Flow`／`Web API Flow`／`Curl+VBS Flow`／`Other Batch`）をそのまま使う。対応が無い
  バッチは`-`とする。共通バッチエンジン（5本）は`共通バッチエンジン`とする（旧`Common`から改称。
  詳細は[使い方]バッチ処理定義書.md 0-4節参照）。分類番号は持たない（バッチ分類名だけで識別する。
  同じ値の数値番号を別途振ると名前と番号の二重管理になるため廃止）。
- ***バッチファイル名*** … **自己採番しない。** `.bat`（／`.vbs`／`.wsf`）の実ファイル名から拡張子を除いた
  ものをそのまま使う（例：`FVCC011`、`COMM_FTP_FVCC011`、`goFVCC011`）。08系
  [バッチ処理定義書]のフロントマター`bat_name`と一致させる（[使い方]バッチ処理定義書.md 0-1節参照）。
  拡張子を落とすと別行のバッチファイル名と衝突する場合（例：`.bat`ラッパーが呼び出す同名の`.py`本体）は、
  実体がスクリプトであることを明示する目的で拡張子を残してよい（例：`SeisanUpdate_new.py`）。
- ***処理概要*** … そのバッチが実際に何を処理するか（呼び出し先の実体、加工内容等）を1文で記載する。
  単なるラッパーの場合は「`〇〇`を呼ぶ薄いラッパー」のように実体を明記する（AZR-417にて
  客先指摘：旧「備考」に混在していた起動方法・周期と処理内容を分離）。**起動時刻・反復間隔等の
  Windowsタスクスケジューラ由来の情報は記載しない**（旧「実行条件」「周期」列は削除。0節参照）。
  バッチの処理内容を要約した日本語名称もここに含めて記載する（旧「バッチ名称」列は廃止し統合。
  ソースコードに記載の無い人手の要約であるため、独立した列としては扱わない）。
- ***参照エンジン（該当時）*** … 本行が共通バッチエンジンを呼び出す薄いwrapper（呼出元ラッパーの
  ソース1行が`call COMM_ftp <ID>`等、呼び出す共通部品が明示されている行）の場合に、呼出先エンジンの
  バッチファイル名を記載する（本行自身のソースコードから読み取れる情報のため対象）。該当しない行は空欄でよい。
- ***備考*** … **「対象外（未使用）と思われる」または「未確認（要客先確認）」に該当する場合のみ記載する。**
  それ以外の補足事項（見積書への未収録、関連バッチとの並列起動関係等）は本列の対象外とし、
  記載しない（特になければ空欄）。この判定は**設計書作成の可否を決めるものではない**（0節参照）。
  ソース調査の結果、そのバッチがどこからも呼ばれていない（呼出元が無い）と判明した場合は
  `対象外（未使用）と思われる`と記載する。調査だけでは判定が難しい場合は`未確認（要客先確認）`
  と記載し、基本設計時に客先へ未使用機能をヒアリングする（AZR-417にて客先指摘）。
